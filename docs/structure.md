# 目录纪律

> 这份文件的存在理由只有一个：**让项目变大之后，任何 agent 都能在十分钟内找到该改哪里。**
> 目录一旦开始语义漂移，项目就开始腐烂。所以这里的规则是硬的，不是建议。

---

## 一、顶层目录：放什么，不放什么

| 目录 | 只放这个 | **不许放** | 上限 |
|---|---|---|---|
| `content/` | 描述"世界有什么"的 TOML | 任何代码、任何生成物 | 每种 kind 一个子目录 |
| `mods/` | 覆写层、官方示例 mod（含 `scripts/` 下的行为 mod） | 基础内容（那是 `content/` 的事） | — |
| `contract/` | 扩展点声明：合法的组件、字段、枚举、kind | 任何运行时逻辑 | **只有 1 个 registry.py**，超过就说明该分层了 |
| `tools/` | 处理内容、检查仓库的命令行工具（编译、热重载、转换、架构检查） | 运行时逻辑、游戏代码 | ≤ 8 个文件 |
| `game/` | Godot 工程：怎么跑 | 生成物、内容数据 | 见下节 |
| `docs/` | 设计、进度、决策、结构 | 代码 | 见下节 |
| `legacy/` | 归档的旧实现，只读 | **新代码** | 冻结，不再增长 |

判断一个文件该放哪，只问一句：**它描述"世界有什么"，还是"世界怎么跑"？**
前者进 `content/`，后者进 `game/`。两边都不属于的，大概率不该存在。

## 二、`game/` 内部

```
game/
├── project.godot
├── main.tscn            入口场景，只有一个
├── scripts/
│   ├── content/         读 pack、把数据变成节点
│   ├── world/           分块、合批、程序化几何、世界组装
│   ├── render/          卡通着色与描边（只有 .gdshader）
│   ├── physics/         碰撞体、刚体、地板
│   ├── player/          角色控制、抓取与投掷
│   ├── hooks/           事件总线与 mod API —— 对外唯一通道
│   ├── mods/            运行时加载脚本 mod
│   └── ui/              生成菜单、HUD（尚未开始）
├── scenes/              可复用的 .tscn，一类实体一个
└── assets/              模型、贴图、音效（按来源分目录，不按类型分）
```

规则：

- **`scripts/` 下最多两层。** 出现第三层就说明某个域的职责已经过载，先拆域再分目录。
- **每个域目录 ≤ 12 个 `.gd`。** 超过就说明这个域在做两件事。
- **单文件 ≤ 400 行。** 超过就拆，拆的时候按"职责"拆，不按"前后半段"拆。
- **一个域只通过显式接口对外**（Godot 里就是 `class_name` + 公开方法）。别用全局单例互相偷看。
- `main.tscn` 只有一个，且它只负责组装，不写业务逻辑。

**这些规则不是建议，`tools/lint_arch.py` 会检查它们**（R1-R3），失败就等于 `check.sh` 失败。
改规则的正确顺序是：先改这一页，再改脚本。反过来做，脚本会变成一份没人同意的法律。

## 三、`docs/` 内部

| 文件 | 作用 | 更新时机 |
|---|---|---|
| `status.md` | 现在在哪、下一步、卡在哪 | **每次会话结束前必须更新** |
| `structure.md` | 本文 | 目录结构变化时 |
| `architecture.md` | 设计与取舍 | 架构变化时 |
| `roadmap.md` | 阶段与产品定义 | 阶段变化时 |
| `decisions/NNNN-*.md` | 每个不可逆决定的理由 | 做决定时，**追加，不改旧文** |

ADR 用四段式，超过一页就说明你在写小说：

```
# NNNN 标题
## 背景（一句话）
## 决定（一句话）
## 被否掉的选项，以及为什么
## 什么情况下应该推翻这个决定
```

最后一段最重要。没有"推翻条件"的决策，会变成没人敢动的教条。

## 四、依赖方向（不许出现反向或循环）

```
contract/  ←──  tools/  ──→  build/产物  ──→  game/
   ↑                                            │
   └──────────── 文档引用 ───────────────────────┘
```

- `contract/` 不依赖任何东西。它是最底层，只声明"什么是合法的"。
- `tools/` 依赖 `contract/`，产出数据文件。
- `game/` **只读产物数据，不 import `contract/` 的代码**。它认的是数据格式，不是 Python 类。
- `legacy/` 谁也不依赖，也不被谁依赖。它只是证据。

出现反向依赖（比如 `tools/` 去读 `game/` 里的东西）就地拒绝，不要"暂时先这样"。

## 五、命名

| 对象 | 规则 | 反例 |
|---|---|---|
| 目录 | 单数名词、小写 | `utils` `misc` `stuff` `new` |
| `.gd` 文件 | `snake_case`，文件名就是职责 | `main2.gd` `test.gd` `temp.gd` `helper.gd` |
| 内容 id | 相对路径去扩展名，`snake_case` | `BoneWalker` `enemy1` |
| TOML 字段 | `snake_case`，单位写进名字 | `speed` → `speed_mps` |
| 函数 | 动词开头 | `data_process()` |

**任何文件都不许叫 `utils` / `helpers` / `common` / `misc` / `base`。** 这类名字等于宣布"我不知道它是什么"，而它会在三个月后变成所有人的垃圾桶。

---

## 六、什么时候该开新目录

只有一种情况：**现有的某个目录里出现了两类互不相关的东西，且以后会各自长大。**

不要因为"看起来整齐"而开目录。空目录和只有一个文件的目录都是负债——它们让下一个人以为那里应该放点什么。

---

## 七、每次提交前的自检

- [ ] 新增的文件放在了正确的目录，且命名符合上表
- [ ] 没有任何目录超过上限（文件数、行数）
- [ ] 没有新增"垃圾桶"名字
- [ ] 依赖方向没有反向
- [ ] `./check.sh` 通过
- [ ] 如果做了不可逆的决定，`docs/decisions/` 多了一份 ADR
