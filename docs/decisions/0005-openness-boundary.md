# 0005 开放度的边界

## 背景

"能模仿任何游戏吗" 是一个必须现在回答的问题，因为它决定扩展点往哪长。
如果答案是"能"，就得为 RTS 的批量查询、回合制的确定性、联机的网络层预留位置；
如果答案是"不能，只做一族"，那些位置现在就不该留，留了会变成死代码和错误的安全感。

## 先拆问题：开放度不是一个维度

四层，逐层变难，**很多平台卡在第三层却对外宣称第四层**：

| 层 | 别人不碰引擎代码能做什么 | 现在 |
|---|---|---|
| L0 数据 | 加道具、敌人、房间，改数值 | ✅ 100%，编译期校验 |
| L1 组合 | 用已有组件拼出新 kind | ✅ 契约里有 `require`，加 kind 不改引擎 |
| L2 外观 | 换模型、配色、贴图 | 🧪 通道实测可行，未接 |
| L3 行为 | 挂一段脚本，在事件发生时做自己的事 | ⚠️ **能执行代码，但没有任何钩子可挂** |
| L4 规则 | 引入一条全新的每帧规则（新系统） | ❌ `SYSTEMS = []`，扩展点只有壳 |
| L5 引擎 | 改物理、渲染管线、网络 | ❌ 故意不开放 |

> **状态更新（2026-11-14，第十一轮）**：上表是这份 ADR 写下时的**快照**，不是现状。
> L2 静态模型覆盖已打通（ADR 0012），L3 钩子 / L4 组件与系统也已打通
> （ADR 0007 / 0011）。当前真实状态以 `docs/status.md` 与 `docs/architecture.md` §5
> 为准；下面「缺的三样东西」同样已经补齐。保留原表是为了让「当时为什么这么判断」
> 可追溯，**不要照着它排下一步**。

**L3 → L4 是分水岭。** "能跑一段代码"和"能加一种玩法"是两件事：
玩法是一条持续参与帧循环的规则，需要系统容器、注册入口、和能被其它系统读到的组件写入。
现在这三样一样都没有。

## 决定

**目标是"一族的平台"，不是"任何游戏"。**

这一族共享同一套基础设施：**第一/第三人称视角 + 空间位置 + 物理碰撞 + 实时循环 + 实体化世界**。
FPS、第三人称动作、生存建造、恐怖探索、物理沙盒、塔防、潜行、载具驾驶都在族内——
它们要的东西是同一批，只是配比不同。

族外的游戏不是"难做"，是**需求互相冲突**：

| 类型 | 它真正缺的东西 | 为什么和本架构冲突 |
|---|---|---|
| RTS | 几千单位、框选、指令队列、战争迷雾 | 本架构的合批是为"渲染便宜"设计的；RTS 卡在 CPU 侧的批量查询与调度，要反向设计 |
| 回合制 / 卡牌 | 确定性状态机、完整存档序列化 | 实时循环是纯负担；3D 完全多余 |
| 平台跳跃 | 逐帧手感：土狼时间、输入缓冲、固定步长 | 手感活在物理参数里，而物理由 Godot 提供 → mod 改不到，只能改引擎 |
| 联机任何类型 | 网络同步、权威服务器、回滚 | 现在零网络代码，且确定性尚未建立（architecture.md 第 8 节标 📐） |
| MMO / 大世界 | 流式加载、LOD、分片 | 当前一室一块，一个 48×40 的房间不能只加载一半（0004 已记此风险） |

## 真正决定开放度上限的，不是扩展点数量

是 **API 表面有多稳定**。

如果 mod 拿到的是 `Node3D`、`MultiMesh`、内部节点路径，那么 mod 生态会把引擎内部结构
**当场固化**：第一天就有人 `get_node("../../chunk_0/MultiMesh")`，之后任何重构都会破坏所有 mod。
GMod 能长出那么多模式，不是因为它扩展点多，是因为它给的是 `Player`、`Entity`、`hook.Add`
这种中介 API——**从不把 Source 引擎内部对象交出去**。

所以铁律：**暴露意图，不暴露结构。**

```
对 mod 开放                          不对 mod 开放
--------------------------------    --------------------------------
spawn(id, position)                 节点树、parent、get_node 路径
apply_impulse(entity, v)            Transform3D 直接赋值
set_field(entity, name, value)      Component 对象的引用
query(radius, component_names)      遍历所有实体
on(event, callback)                 订阅引擎内部信号
```

## 缺的三样东西（P1 之前必须定）

1. **钩子表**：事件名 + 参数 schema + 触发时机，进契约（`registry.py`），随 schema 导出。
   没有它，mod 只能"加内容"，不能"改行为"。
2. **系统容器**：`SystemSpec` 已经有 `priority` / `reads` / `writes`，但没有任何注册与调度实现。
   mod 系统要能被引擎按同样的优先级规则插进去，否则"新玩法"只能靠改引擎。
3. **mod API facade + `api_version`**：包一层，只暴露上面那张左表。
   `api_version` 必须随 facade 走，否则 mod 无法声明"我依赖哪一版接口"。

**这三样要在 P1 之前定，不能之后补。** P1 要写抓取、投掷、放置——
如果那时不埋钩子，这些行为就全是引擎硬编码，mod 只能看不能改，
之后补钩子等于把已经写好的逻辑全部返工一遍。

## 什么情况下应该推翻这个决定

- **用户明确要做 RTS 或联机**：本 ADR 的"一族"结论作废，需要重做批处理层（空间索引 + 批量查询）
  与确定性层（固定步长 + 状态哈希），这是两条独立的大工程，不是加扩展点能解决的。
- **mod 生态真的起来了**：facade 会变成瓶颈（"这个 mod 想要我没暴露的接口"）。
  届时的正确做法是**加宽 facade**，而不是开一个 `unsafe.get_node()` 后门——
  后门一开，前面所有的稳定性承诺全部失效。
- **Godot 上游提供了沙箱**：0003 的"mod 完全权限"结论要重审，`scripted` 级别可以降级为可信。
