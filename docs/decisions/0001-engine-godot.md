# 0001 用 Godot 4 做运行时，自研渲染器归档

日期：2026-11-13
状态：有效

## 背景

最初的方案是自研 C++17 + OpenGL 3.3（零第三方依赖），理由是"内容已经是数据，
不需要可视化编辑器，所以自研最贵的那一项成本消失了"。这套东西已经跑起来了：
3 万条内容、3 次 draw call、能走能转视角。

但需求在澄清之后变了：**项目不是"一个内容很多的游戏"，而是"一个别人能往里面加东西的平台"**。
这推翻了原来那个推论的前提。

## 决定

运行时换成 **Godot 4**，自研渲染器归档到 `legacy/cpp-renderer/`。

内容层（`content/`、`contract/`、`tools/contentc.py`）全部保留，因为它们与引擎无关。

## 被否掉的选项

**继续纯自研。** GMod 形态需要的不只是渲染器：脚本层、资源覆盖、物理、网络、打包。
自研每一样都是一年起的投入，而项目是单人 + agent 驱动、时间不固定。
更要命的是维护成本结构：自研的债是复利的（同时维护游戏和引擎），引擎的债是分期的。

**Bevy（Rust）。** 工具链在，ECS 也顺。但沙盒需要的物理、导航、音频、UI 在 Bevy 生态里
成熟度不足，得自己拼装。"Rust 重写的 Minecraft 很快"这类例子不适用：体素区块网格化的
瓶颈在顶点与区块调度，而沙盒的瓶颈在物理与网络。

**Unity / Unreal。** Linux 原生支持、开源可改、单文件导出这三条都不满足。

## 这个决定的价值不在性能

Godot 会被选中的真正原因是它内置了平台需要的四样东西：

| 平台需求 | Godot 内置 |
|---|---|
| 资源覆盖（MC 资源包） | `ProjectSettings.load_resource_pack()` |
| 模组加代码（GMod 插件） | 运行时 `load()` 脚本 |
| 沙盒物理 | Jolt / RigidBody3D |
| 打包分发 | 导出 Linux/Windows 单包 |

还有一条对"agent 驱动开发"特别重要：**主流引擎的 API 在训练数据里。** 私有框架每次
新会话都要重新理解，成本随项目变大而爆炸。

## 什么情况下应该推翻这个决定

1. Godot 的单帧提交开销在真实目标场景（几百个动态刚体 + 玩家建造物）下成为瓶颈，
   且性能剖析确认瓶颈在引擎而没有绕过手段。
2. Godot 的 mod 加载（运行时 `load()` 脚本）在导出后的包里有无法绕过的限制，
   导致 P3/P5 阶段做不出来。这一点目前**只是推测，尚未验证**——P3 开工时要先做最小验证。
3. 4.x 升级连续两次带来破坏性变更且社区未跟上，导致维护成本超过自研。

第 2 条是当前最实际的风险，应当尽早验证，而不是等到 P5。
