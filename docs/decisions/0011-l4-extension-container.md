# 0011 L4 扩展容器：组件与规则由 mod 声明

## 背景

L3 已经能挂事件、能调 `api` 的动词，但一个新玩法仍然要引擎改代码：
`contract/registry.py` 里的组件是固定 13 个，`game/scripts/systems/` 里的系统也是固定两个。
用户明确要求「先做架构上的事，把开放度打开，内容靠开放度加」——所以先补这个分水岭，
不再往 `content/` 里堆具体房间、道具或玩法。ADR 0005 把 L3 → L4 定义为
「能引入一条全新的、持续参与循环的规则」，本 ADR 决定它具体长什么样。

## 决定

1. **mod 可以用 `kind="component_spec"` 声明新组件**，字段带类型、默认值、范围 / 枚举；
   编译器把声明导出进产物的 `extensions.components`，引擎合并进 `pack.schema.components`。
   基础内容也可以用同一种文件声明组件，但**不能带可执行代码**。
2. **mod 可以用 `kind="system"` 声明新规则**：`source` 指向自己的 `.gd`，
   `reads` / `writes` / `priority` / `period` 是权限清单与调度参数。
   脚本只有 `step(ctx, api)` 一个入口，跑在固定节拍上，不是每渲染帧。
3. **系统只拿到不透明 handle 和 `ctx.read/write`**，拿不到节点、Transform3D、组件对象。
   `ctx` 按该系统声明的 `reads` / `writes` 做白名单；写值还要过字段类型 / 范围 / 枚举。
   自定义组件的可变状态由引擎按 handle 保存，**不进存档**（存档仍只存玩家的动作）。
4. **带 `system` 的 mod 与带 `script` 的 mod 同级**：默认拒绝，必须 `--trust=<id>`。
   编译器、引擎各自独立按「有没有可执行代码」算真实级别，不信作者声明。
5. **组件名不能覆盖契约内置组件，系统优先级从 100 起且不许重复**。
   冲突在编译期和运行时各拦一次；`contentc --selftest` 与探针各有断言。

一句话：**引擎仍然不认识任何具体内容，但认识「如何装载别人声明的规则」。**

## 被否掉的选项，以及为什么

- **直接把 mod 脚本塞进 hooks 的 `tick` 事件**：那只是 L3 的定时器，读不到新组件、
  没有读写集、没有优先级，两个 mod 同时改一个状态时会静默互相覆盖。
- **让 mod 注册组件时上传任意 GDScript 类型 / Resource**：等于把引擎内部对象交出去，
  违反 ADR 0005 的「暴露意图，不暴露结构」，也会让生态立刻钉死内部结构。
- **把自定义组件状态写进存档**：存档会变成任意 mod 数据的垃圾桶，卸载 mod 后无法解释；
  本项目的存档边界仍是「只存玩家的动作」。
- **继续只加内容（多 spawner / interaction）**：能把这一版变好玩，但每加一种玩法都要改引擎，
  与「内容靠开放度加」正相反。那些是验证 L4 的后续内容，不是本轮前置条件。

## 什么情况下应该推翻这个决定

- **需要每帧级手感规则**（输入缓冲、物理求解、动画状态机）：固定节拍和 `ctx` 的中介成本
  会挡路，应把规则收进引擎自带系统，而不是放宽 mod 到每帧。
- **自定义状态必须跨会话保存**：需要单独设计「mod 状态段 + 版本迁移 + 卸载清理」，
  不能顺手把 `ctx.write` 的结果塞进 `slot0.json`。
- **同时装入几十个系统且固定节拍成为瓶颈**：要先做系统预算 / 分组调度，
  不能靠取消 `period` 下限让 mod 自己抢主循环。
