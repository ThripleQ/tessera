# 0006 卡通渲染与物理的身份问题

## 背景

目标从"能出画"变成"能玩"：要有可操控的角色、动漫风的画面、会动的物理世界。

三件事里有两件半是相互牵制的，必须先说清楚。

## "动漫风不吃性能"这个判断，对了一半

**对的那一半**：卡通着色的逐像素成本确实比 PBR 低一个档。PBR 每像素要算 GGX 分布、
菲涅尔、几何遮蔽，卡通只要一句 `N·L` 量化成两档。在**软件光栅**（这台机器没有
`/dev/dri`，只有 llvmpipe）上，这个差距被放大到决定性的程度。

**不对的那一半**：原神那种效果的重量不在着色模型，在**资产与后处理**——
几万面的角色高模、面部 SDF 阴影贴图、表情 blend shape、头发各向异性、Bloom 与色调映射。
它看起来"不重"是移动端大量砍效果的结果，不是风格本身轻。

**所以本项目的诚实定位是：卡通色块，不是原神的脸。**

用程序化几何能做出色阶、描边、高饱和配色、正确的头身比——这些是"认得出来是动漫角色"
的必要条件。但**做不出面部表情、眼睛高光、服装细节**，那需要贴图管线，
是 P3 资产层的事，不是着色器能解决的。

## 决定一：渲染走自定义 toon shader，不调 StandardMaterial3D

两条 pass：

| pass | 文件 | 作用 |
|---|---|---|
| 主 | `game/scripts/render/toon.gdshader` | `light()` 里把 `N·L` 量化成两级色阶 + 边缘光 |
| 描边 | `game/scripts/render/outline.gdshader` | `next_pass`，`cull_front` + 沿法线外扩 |

**为什么一定要自己写 `light()`**：卡通的关键不是"看起来平"，而是**明暗交界是一条硬线**。
PBR 的连续渐变永远出不来这条线，而这条线是"动漫感"的主要来源，比多边形数重要得多。

**描边为什么用反向外扩**：Compatibility（OpenGL 3.3）没有几何着色器，也不提供免费的
深度纹理，所以屏幕空间边缘检测做不了、也不划算。把模型吹大一圈只画背面，是这里唯一
可行且便宜的路。

外扩宽度必须跟着视图距离缩放，否则远处糊成黑边、近处细得看不见。

## 三条实测结论（都在这台 llvmpipe 上跑过）

1. **`light()` 在 Compatibility 下可用**，`DIFFUSE_LIGHT` / `LIGHT_COLOR` /
   `ATTENUATION` / `NORMAL` / `VIEW` 都能拿到。
2. **`next_pass` + `render_mode cull_front` 可用**，描边正常出图，且对 MultiMesh 生效。
3. **亮度必须显式标定。** Compatibility 喂进 `light()` 的 `LIGHT_COLOR` 与 Forward+
   不是同一个量级：只除以 `PI` 会过曝成一片白（实测整个世界变成纯白，色阶完全消失）。
   所以 `toon.gdshader` 里留了一个 `light_gain` 显式旋钮，值是**实测校准出来的**，
   不是物理量。换渲染器时只改这一个数字，不用重写光照模型。

## 决定二：静态合批，动态独立

这是本轮唯一的**结构性**决定，因为它来自一个无法调和的冲突：

```
渲染要合批  →  MultiMesh：一个节点，N 个实例，一次提交
物理要身份  →  每个物体一个 RigidBody3D，独立变换、独立质量、独立质心
```

两者无法共存。硬凑的结果是"整个房间只能被整体推动"这种荒谬行为。

所以按数据分流：

| 数据 | 渲染 | 物理 |
|---|---|---|
| 无碰撞的布景 | MultiMesh（合批） | 无 |
| 有碰撞、`dynamic = false` | MultiMesh（合批） | `StaticBody3D`（不可见的壳） |
| `dynamic = true` | 独立 `MeshInstance3D` | `RigidBody3D` |

**判断依据全在数据里**：`collider.dynamic`。引擎不知道哪个是箱子、哪个是怪（铁律 2）。

## 代价，如实记下

- **动态物体每一次提交都是独立的。** 当前 14 个木箱 = 14 次提交，
  而 9 个怪 + 3 种网格的静态部分只要 2 次。这就是"物理"的价格。
  当前世界：`静态 2 次 + 动态 14 次`。
- **描边让每批提交翻倍**（主 pass + 描边 pass）。所以描边是**可选能力**：
  地板、世界底板都显式传 `outline = 0`，不挂第二个 pass。
- 沙盒里同屏几十个刚体是常态，所以这个数字必须一直打印在 `check.sh` 里，不能藏。

## 顺带建立的一条硬约束

`contract/registry.py` 里的 `MESHES` 三角形数**改成实测值**，且引擎自检会拿它和自己数
出来的比，不一致直接失败。

原来的注释说这些是"规划值，不参与预算判断"——那意味着数字可以长期说谎。
实测时就抓到了漂移：`shade_lowpoly` 契约写 36，实际 48。

预算失真是这个项目最不能接受的一类错误，因为它让人以为世界还装得下。

## 什么情况下应该推翻

- **换到 Forward+ 或 Vulkan**：`light_gain` 要重新标定，描边可以换成屏幕空间边缘检测
  （更均匀，且不增加提交次数）。
- **同屏刚体超过一两百个**：独立提交会成为瓶颈，届时改成"动态物体也进 MultiMesh，
  每帧回写 instance transform"。代价是每帧 CPU 侧的上传，且要和物理帧对齐。
- **引入贴图资产管线**：卡通着色的 `ALBEDO` 要改成从贴图取，`COLOR` 从"主色"降级为
  "染色系数"。这一步会牵动 `mods/` 的资源覆盖规则（ADR 0003 的外观通道）。
- **要做面部表情**：只能走贴图 + blend shape，程序化几何这条路到头了。
