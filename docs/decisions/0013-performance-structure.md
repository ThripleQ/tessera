# 0013 性能：守结构，不守毫秒

## 背景

用户 2026-11-20：*"检查一下项目，看看有没有性能问题，现在开始优化性能"*。

动手之前先核对了"性能数字是怎么来的"。结果是：**项目追了十几轮的帧时基线
根本没在测游戏**。`game/probes/perf.gd` 量的是无头主循环的帧间隔，
而空场景跑同一个循环也是 6.90 ms —— 引擎在无头模式下的主循环自己就有
约 6.8 ms 的地板（实测最小 2.13 ms、最大 23.32 ms）。

佐证：把 23 个刚体的 `continuous_cd` 全部关掉，帧时一点没变（6.90 → 6.90）。
那说明这个数字对世界里的工作量不敏感，它不能用来判断任何改动有没有变快。

同一轮里还量出三处真实的每帧浪费：

- `Camera3D.get_frustum()` 在**逐件剔除**里被调用：26 件东西、每帧 26 次，
  每次分配一个数组加 6 个平面。
- `PhysicsRayQueryParameters3D.create()` 在视线射线里每帧新建：准星一帧问两次落点，
  外加一条新数组。
- `MESH_LIB.toon_material_for()` 给每个刚体、每件静态物各造一份 `ShaderMaterial`：
  23 件东西就是 23 份，而它们只差一个颜色参数。

## 决定

### 1. 性能只认三种证据，墙上帧时不算

- **结构指标**：节点数、材质份数 / 引用次数、绘制项、物理活跃物体、接触对数。
  与机器无关，可以设红线。
- **同机成本对拍**：同一段代码的新旧两种写法，各跑 120 遍 × 5 批，**取最小值**。
  噪声只会让测量变慢、不会让代码变快，所以最小值最接近真实成本。
- **墙上帧时**：打印，但**不设断言**，退出码不受它影响。

`check.sh` 第 13 步（`game/probes/budget.gd`）只断言前两种。

### 2. 材质的单位是配色，不是物体

`toon_material_for(color, outline)` 按 `(配色, 描边宽度)` 缓存共用。
23 件东西 32 次引用只产生 10 份材质。

**染色必须 copy-on-write**：`api.tint` 先 `MESH_LIB.unshare()`，把共享的那份复制成
私有的一份再改。否则"给一个箱子染色"会变成"给所有同色箱子染色" ——
功能全绿、没有任何报错，只有玩家觉得这游戏有点怪。

### 3. 一帧一次的东西只建一次，但结果不许缓存

视锥每帧一份（`culling.snapshot()`），逐件用 `should_draw_in()` 复用。
射线查询对象复用一份，但**每次都真打**。

试过按"射线参数相同"缓存射线结果，生成菜单探针立刻红：世界在同一帧内也会变
（刚放下的柱子就落在射线里），而参数没变。射线的答案属于"现在"。

### 4. 不为了数字去动物理开关

`continuous_cd` / `contact_monitor` 都在 `solids.gd` 里，看起来是"可疑项"，
但 A/B 实测关掉 CCD 对帧时没有影响，而它防的是穿墙 —— **没有证据就不动**。
真要调，得先在真机上量出物理步进的真实占比。

### 5. 顺带削掉两处"每帧做无用功"

- `locomotion` 只在朝向变化超过 1.5 度时才写 `rotation`
  （写 rotation 要穿过物理服务器，比算一次点积贵得多）。
- `vitals` 对"没有 hp 记录"的刚体跳过死亡检查：掉血的唯一来源是撞击，
  它一定会写下这条记录。

## 被否掉的选项，以及为什么

| 选项 | 为什么否 |
|---|---|
| 继续用墙上帧时当红线和基线 | 它测的是引擎在无头模式下的节流，空场景同样 6.90 ms；用它判断改动会让"变快了"和"没变"看起来一样 |
| 给射线结果做跨帧缓存 | 世界在同一帧内也会变；生成菜单探针当场红 |
| 给每件物体保留独立材质 | 保证隔离，但材质数 O(物体数)，真机上每次状态切换都是钱；copy-on-write 已经拿到同样的隔离 |
| 关掉 CCD / contact_monitor 换帧时 | 没有实测收益，却会削弱物理正确性和伤害事件；属于"为了数字改行为" |
| 把系统步进降到 30Hz 来省时间 | 移动手感和伤害响应都会变，而当前常态（23 刚体 0.38 ms/拍）根本不缺这点时间 |
| 把热点逻辑改成 C++ / GDExtension | 现在没有这个需求；而且会给"换一个 agent 也能十分钟看懂"这条要求加一大块门槛 |

## 现在的数字（本机 i5-7200U，无 GPU）

| 场景 | 指标 | 优化前 | 优化后 |
|---|---|---|---|
| 常态 23 刚体 | 剔除 26 件 | 0.248 ms | 0.132 ms（省 47%） |
| 常态 23 刚体 | 材质 | 23 份 | 10 份 / 32 次引用 |
| 常态 23 刚体 | 视锥 | 26 次/帧 | 1.00 次/帧 |
| 预算上限 119 刚体 | 剔除 122 件 | 1.45 ms | 0.83 ms |
| 预算上限 119 刚体 | 系统步进 | 3.29 ms/拍 | 2.7~3.1 ms/拍 |

**压力模式（`--stress`）把世界填到预算上限再测**：96 件是硬顶，
所以"最坏情况"是可枚举的，可以现在量，而不是等玩家撞上。

诚实的一条：预算上限下系统步进 2.7~3.1 ms/拍已经是 GDScript 的合理量级，
不是缺陷。再往上要么减内容，要么改架构（GDExtension），后者是另一个决定。

## 什么情况下应该推翻这个决定

1. **真机上发现材质共用没有减少状态切换**（例如驱动/渲染器把同 shader 不同实例
   也当成不同批次）——那么共用只省内存不省提交，判断要重做。
2. **需要按实例改材质参数**（每个物体的粗糙度、贴图偏移等）——那时应该走 shader 的
   `instance uniform`，而不是回到"一件一份材质"。
3. **导出包上能稳定测量帧时**——那时可以把帧时重新变成断言，但要带机器指纹，
   绝不能让 CI（弱机器）和开发机互相打架。
4. **同屏刚体数逼近预算上限时常态掉帧**——那说明该做"可见 vs 激活"分离（架构文档
   第 6 节标着 📐 的那一条），而不是继续微优化。
