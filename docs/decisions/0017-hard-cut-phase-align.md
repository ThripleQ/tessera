# ADR 0017：动画切换用硬切 + 相位对齐，不用交叉淡化

- 日期：2026-11-21
- 状态：已落地（第十九轮）
- 相关：ADR 0015（步态匹配）、ADR 0016（FPS 训练场）

## 背景

用户对人物的要求是 *"gta5 里人物走路跑步流畅自然。我们也要做到"*，
并且 *"不要死磕某个方法，之前的自动化跟脚不好用就不用"*。

ADR 0015 解决了"匀速走的时候脚不打滑"，但那只是**稳态**。
换档那一帧（走路切跑步）脚会跳一下 —— 而这件事**任何速度数字都测不出来**：
脚跳 10 厘米时，速度依然是 1.04 m/s，滑移依然是 0.005 m/s。
所以它得单独量，单独治。

## 决定

1. **取消交叉淡化，一律硬切。** 三条都是实测出来的：
   - 带淡化的 `play()` 之后调 `seek()`，播放位置会跟着走，
     但**骨架纹丝不动** —— 淡化期间 seek 根本不驱动骨骼。
   - 淡化期间脚持续往身体中心收，相对速率约 **0.8 m/s** —— 那是**真的在滑**，
     而且持续 0.18 秒；比 1 帧的姿势突变显眼得多。
   - Godot 的 `play()` **不重置播放位置**：新片段会从旧位置接着播。
     两条片段长度不同时，接着播就等于从一个错乱的相位开始。
2. **换步态档时对齐相位**：切换前记下相位（播放位置 / 循环长度），
   切换后 seek 到同一个相位。这样"左脚刚落地"这个时刻在两条动画里是对齐的。
   前提是两条片段一个循环里的**步数相同**（KayKit 的走和跑都是两脚一循环），
   于是"时间相位相同"就等于"步相位相同"。步数不同的包不适用。
3. **起步给初速度**（走速的 70%）：真人第一步就迈出去，不是从 0 慢慢爬。
   爬的过程里动画倍率会小到 0.2，脚步变成慢动作；而速度低于阈值时播的是待机，
   脚不动身体在飘，那是"滑着走"。
4. **停车在"最低档速度 × 倍率下限"以下时直接归零**：0.73 × 0.45 = 0.33 m/s。
   比它慢时倍率会被下限夹住 —— 动画还在往前送，身体已经慢下来，
   脚在身后拖着走。

## 效果（check.sh 第 18 步实测）

- 换档那一帧，脚多挪 **0.055 m**；把相位对齐**关掉**是 **0.738 m** —— 差 13 倍。
  对照组是必须的：没有它，"脚没跳"可能只是因为两条动画的脚本来就离得近。
- 起步与停车全程"补不掉的滑移" **0.000 m/s**。

## 代价（明知，故写下来）

- **躯干姿势在切换那一帧会硬变**（走 → 跑）。这是明知的取舍：
  脚的连续性比一帧的姿势突变重要 —— 脚跳出去几厘米会被眼睛一直盯着，
  姿势变一帧只会被读作"他加速了"。
- 状态切换（待机 ↔ 走路、跳跃、落地）也一并改成硬切。
  待机 → 走路是"起步"，走路 → 待机是"站定"，这两个姿势变化本来就该有一帧的突兀；
  换来的是脚不再拖 0.18 秒。

## 什么情况下应该推翻

- **如果资产里有了专门的起步 / 刹车动画**（起跑、站定片段）：回到"用它们"，
  相位对齐继续保留 —— 它对任意两条片段都成立。
- **如果要做动作融合**（跑步时侧身掏枪、半蹲瞄准）：硬切不够用，
  那时才需要自己搭两棵骨架的混合系统。那时的成本与今天的取舍不是一回事。
- **如果 Godot 哪天让 blend 期间的 seek 生效了**：交叉淡化可以重新考虑 ——
  但淡化期间那 0.8 m/s 的拖脚仍然存在，所以大概率还是硬切。
