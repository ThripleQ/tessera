# 0008 mod 装载与存档

- 状态：已实现
- 日期：2026-11-14
- 影响面：`tools/contentc.py`、`game/scripts/mods/`、`game/scripts/save/`、`check.sh`

两件事放在一份 ADR 里，因为它们回答的是同一个问题的两面：
**什么东西属于"引擎"，什么东西属于"玩家"。**

mod 是"别人做的内容"，存档是"你自己做的改动"。两者的共同点是：
引擎不拥有它们，只负责让它们安全地进出。

---

## 一、mod 装载

### 背景

上一版 mod 是"仓库里的一个 TOML"：加东西必须放进 `mods/`、重新编译整个内容包、
路径还写死在 `source = "mods/scripts/x.gd"`。那是仓库内的插件，不是平台。

判据很简单：**能不能收到一个陌生人的目录，直接让它生效？** 不能，就不是平台。

### 决定

一个 mod = 一个目录，自带元数据、内容、脚本、和编译产物：

```
mods/<id>/                 或 user://mods/<id>/
  mod.toml                 [mod] id / name / version / api_version / level / author
  content/*.toml           内容；脚本路径相对本目录
  scripts/*.gd             可选
  content.pack.json        产物，引擎只读它
```

引擎侧三步，顺序本身就是安全的一部分：

| 步 | 做什么 | 顺序错了会怎样 |
|---|---|---|
| `discover` | 扫目录读产物，**不加载** | 先合并再检查，等于把坏内容装进世界才发现 |
| `resolve` | 按授权决定谁进来，未授权的整包挡住 | 只合并数据不跑代码 → 玩家看到"装了却没生效" |
| `merge` | 按 id 字典序叠加，覆写要打印出来 | 顺序不定 → 同一个 mod 集在两台机器上长出不同的世界 |

### 为什么引擎不解析 TOML

引擎里再写一个 TOML 解析器 = 两份编译器、两套行为。它们只在某个 mod 的某个字段上
不一致，而那个字段可能三个月没人用到。

所以：**作者写 TOML（人手舒服），产物是 JSON（机器原生），中间那层永远只有一份。**

代价是 mod 作者需要跑一条命令：
`python3 tools/contentc.py --mod mods/<id> --base content`。
这和 Minecraft 的 mod 要打包成 jar 是同一类要求：发布者打包，玩家只解压。

### patch 型 mod 怎么变成"差异"

`kind="patch"` 的语义是"作用在已解析完继承链的实体上"，所以它必须能看见基线。
编译时把基线编两遍（不带 mod / 带 mod），取差异作为产物。

于是产物是**"我改变了什么"**，不是"我抄了一份世界"。三个直接好处：

1. 多个 mod 可以叠加
2. 引擎里不需要第二个 patch 求值器
3. 一个只改了 3 个敌人的 mod 不会声称自己带了几百条内容（`counts` 按 diff 重算）

### 授权：默认拒绝

Godot 没有 GDScript 沙箱（ADR 0003 实测 `OS.execute` 返回 0）。既然拦不住"能干什么"，
就只能在"能不能进来"上做区分，而那个开关必须由玩家按下。

两条不能妥协的判定：

**1. 级别由内容决定，不由声明决定。**
作者可以把带脚本的 mod 写成 `level="data"` 来跳过授权。
所以编译器算一遍真实级别、引擎再独立算一遍（产物是外部文件，也会被手改）。
实测过：伪装成 `data` 的脚本 mod 会被按 `script` 处理并挡住。

**2. 未授权 = 整包挡住，不放一半。**
只合并数据、不跑代码，玩家会看到"装了却没生效"，比直接拒绝更让人困惑；
而且下次授权后世界状态会突变。

开关是命令行：`./run.sh --trust=<id>`。没有 UI 之前它比 UI 更诚实 ——
玩家必须自己敲出 mod 的 id，不能一路点"下一步"过去。记录写在 `user://mods.json`。

### 一条结构约束

**基础内容（`content/`）里不许出现 `kind="script"`。**
基础内容永远被信任（它在仓库里、随引擎发布），它一旦能带脚本，
就存在一条绕过授权闸门的通道——而且是最容易被人忽略的那条。自检会拦。

## 二、存档

### 决定：只存玩家的动作，不存世界

```json
{ "version": 2, "saved_at": "...",
  "player": {"pos": [x,y,z], "yaw": 0.0, "pitch": -0.16},
  "bodies": [{"id": "prop/crate", "p": [..], "q": [..], "v": [..], "w": [..]}],
  "props":  [{"id": "prop/pillar", "p": [..], "q": [..]}] }
```

没有房间、没有地面、没有静态障碍。理由：

- 世界是内容决定的，重跑一次就有
- 一旦存了静态世界，改一个房间尺寸就要写迁移代码
- 而那种迁移保护的是"上次的样子"，不是"上次的成果"

**v2 补上了 `props`**（玩家从菜单放下的静态物）。这是同一句话的延伸，不是推翻：
房间里的柱子和玩家放的柱子长得一样、数据也一样，但**归属不同** ——
前者是内容的形状（不存），后者是玩家的动作（要存）。世界用 `world.props` 单独记着后者。
不补这一项，"从菜单放下的东西关窗就没了"和这份 ADR 的承诺直接矛盾。

v1 的存档照样能读（少一个列表而已）。拒绝它换来的只是我们少写三行迁移代码，
代价是玩家觉得"我的进度没了"。

`props` 里**不记录"它是静态的"**：读档时重新问一遍内容"这东西现在还静不静"。
所以有人把一个原型改成 `dynamic = true` 之后，旧存档里的那根柱子读回来会变成会滚的箱子——
那是正确行为（铁律 2）。

### 为什么是 JSON 而不是二进制

存档要能被打开看、被人手改、被 diff。玩家改坏了自己的坐标，
游戏应该告诉他哪里不对，而不是拒绝加载整个文件。

### 三条顺序上的硬要求

| 要求 | 违反后的表现 | 为什么难查 |
|---|---|---|
| 读档在玩家和世界都就位之后 | 玩家被挪回起点，或者被挪到上一帧的位置 | 只在有存档时出现 |
| 先清空再重建 | 每读一次档物体数量涨一轮 | 只在**第二次**读档时出现 |
| 清空后 `api.forget_all()` | mod 下一次 `api.pos(h)` 读已释放对象 | 只在带 mod 且读档时出现 |

三条都是"第一次测试完全正常"的那种 bug。

### 「读不出来」不等于「没有存档」

前者要报错并明说原文件没动，后者才静默开场。
混淆这两件事会让玩家以为自己的世界丢了，而实际上只是这一次读不进来。

### 自动保存：关窗口时

这是玩家唯一一定会做的结束动作。没有它，"关了再开东西就没了"
会让整个沙盒看起来是个玩具。`F5` 手动存、`F9` 读档、`--fresh` 跳过读档。

`--fresh` 不是调试便利，是**必需品**：截图探针和回归测试需要一个干净的世界，
否则每次跑出来的画面都取决于上一次留下了什么。

### 验收怎么覆盖它

无头自检只走到 Plan 层，不实例化玩家、不跑物理，所以坐标编码、刚体重建、
handle 作废全在它的覆盖之外。而这类代码的错法是"看起来存了，读回来差一点"。

所以有 `game/probes/save_roundtrip.gd`，接在 `check.sh` 第 6 步：
推一个箱子 → 存 → 再推走 2 米 → 读档 → 要求它回到存档位置（误差 < 0.15 米），
同时要求刚体数量不变、玩家位置也回来了。

注入过违规验证它有牙齿：让 `apply` 不还原玩家位置，`RESULT` 立刻变成
`位置 OK / 数量 OK / 玩家 FAIL`。

`TESSERA_SAVE_SLOT` 环境变量保证它**绝不动玩家真正的存档**。
一个会吃掉玩家进度的测试迟早会被关掉，而关掉的测试等于没有。

## 什么情况下应该推翻

### mod 装载

- **如果 mod 作者普遍不会跑 Python**（比如面向非技术玩家）：要在引擎里内置
  一个最小的 TOML 解析器，但必须先解决"两份编译器行为一致"的问题，
  比如把编译器做成能生成对照表的形式，让 `check.sh` 逐条比对
- **如果开始出现"mod 依赖 mod"**：现在的顺序是 id 字典序，
  没有依赖解析。真要支持依赖，得引入拓扑排序和版本约束，
  那是另一个量级的东西
- **如果 mod 需要改契约**（加组件、加钩子）：那是 L4，现在完全没有。
  届时的关键是"谁拥有契约"——如果每个 mod 都能加钩子，
  `bus.gd` 的"只发契约里的"这条约束就会失效
- **如果出现了真正的沙箱需求**（比如要托管玩家上传的 mod）：
  Godot 做不到，得换执行模型（WASM 或独立进程 IPC）

### 存档

- **如果开始有"多个世界/存档槽"**：现在的 `slot0.json` 是硬编码的。
  加槽位不难，难的是"玩家怎么知道哪个槽是哪个世界"——那需要世界标识
- **如果 mod 需要在存档里保存自己的状态**：现在 mod 的状态完全不存。
  加这个要先定"mod 卸载后它的状态怎么办"，否则存档会变成一堆无法解释的孤儿数据
- **如果静态世界也需要可变**（比如玩家能拆墙、挖地）：
  那时静态世界就不再是"内容的形状"了，得存。届时的关键是按块存差异，
  不是存整个世界
- **如果存档需要跨版本兼容**：现在 `version` 不等就拒绝。
  真要做迁移，每个版本要有一个迁移函数，并且要有"用旧存档跑一遍"的回归测试
