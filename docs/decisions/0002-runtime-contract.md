# 0002 运行时怎么拿到契约

## 背景

契约只存在于 `contract/registry.py`（Python），而引擎读的是 `content.pack.json`。
两份东西天然会漂移：契约里把 `max` 改名成 `max_hp`，编译期校验全过，引擎那边
还按 `max` 读，字段静默变成默认值——三个月后才发现某个怪血量永远是 0。

迁移到 Godot 之后这个缝更明显：引擎不可能 `import` 一个 Python 模块，它只认数据。

## 决定

**编译期把 `registry` 导出成 `pack.schema`，随内容包一起走。引擎只读这份数据。**

1. `tools/contentc.py` 的 `build_schema()` 从 `contract/registry.py` 生成
   `schema.components / kinds / brains / loot_tables / meshes`。
2. `pack.gd` 把 `schema` 当硬要求：**缺 schema 段的内容包直接拒绝加载。**
   理由是没有它，引擎就无法知道自己漏实现了什么，覆盖度会显示成一个好看的假数字。
3. 自检时校验 `内容用到的组件 ⊆ 契约声明的组件`。编译期已经查过一遍，运行时再查
   是为了防"旧 pack 配新引擎"——那种情况下编译期检查根本没跑过。
4. 引擎侧的**实现清单**放 `game/scripts/content/components/`，一个组件一个 `.gd`。
   **契约说世界能有什么，实现清单说引擎现在能处理什么，两者之差就是待办。**
   覆盖度按"内容实际用到的组件"算，不按契约全集算——没被内容用到的组件，
   没实现也不影响这一版能跑。

这条规则的本质：**schema 是唯一真相的搬运，不是第二份真相。**
它永远由 `registry.py` 生成，手改会被下一次 `check.sh` 覆盖。

## 被否掉的选项，以及为什么

| 选项 | 为什么否 |
|---|---|
| 引擎侧再写一份 schema 校验 | 两份真相。改契约时总有一边漏掉，而漏掉的那边不会报错 |
| 引擎直接读字段，不建实现映射 | 组件改名后静默失效，没有任何一处会失败。这是最贵的错法 |
| GDExtension 把 Python 契约嵌进引擎 | 让引擎依赖 Python 运行时；为一个静态声明付动态成本 |
| 只靠编译期校验，包里不带 schema | 无法回答"引擎实现覆盖了几成"，也无法防旧包错配 |

## 什么情况下应该推翻这个决定

- **schema 体积超过内容本身。** 组件涨到几百个时，全量导出会喧宾夺主，改成按
  `--schema-subset` 只导出内容实际用到的。
- **要做联网或录像回放。** 那时 schema 必须带哈希并参与握手，防止两端字段不一致
  产生"看起来同步了其实没有"。届时本 ADR 升级为 versioned schema。
- **引擎侧引入第二个消费方**（比如独立的编辑器或服务端校验器）。一旦有两个消费方，
  就要重新讨论"schema 是数据还是接口"，不能继续按现在的单消费方假设走。
