# 长远布局

> 写于 2026-11-13，同日重写一次。
> **第一次写的时候我判断错了方向**：我把它当成"一个内容很多的游戏"来排，而他要的是
> "一个别人能往里面加东西的平台"。这两件事的架构重心完全不同。
> 这份文档是给下一个 agent 的交接材料，每次开工先读这一页。

---

## 一、需求：他要的不是游戏，是平台

原话：「我想让游戏充满创造力，什么都能有，都能加，或者改。就像 gmod 那样。」
以及：「画面也是开放的，可修改的，就像 mc 那样。」

这两句话定义了产品的本质，而且把"题材"这个问题永久取消了——**沙盒游戏没有题材**。

| # | 需求 | 真实含义 |
|---|---|---|
| 1 | 3D 沙盒，像 GMod | 玩家能自由拿、放、堆、扔、造 |
| 2 | 什么都能加、能改 | 第三方（和未来的他）不改引擎就能加内容**和行为** |
| 3 | 画面可改，像 MC | 资源覆盖包：换贴图/模型不用改代码 |
| 4 | 公开发布 | Linux + Windows 包，别人能装、能跑、不崩 |
| 5 | 时间依兴趣 | 每个阶段必须能独立停下，停下时东西是能玩的 |
| 6 | 靠 agent 开发 | 选型第一准则是"换个 agent 也能看懂" |

### 三个"开放"层次 —— 三层都已打通

这是最关键的差距分析。GMod 和 MC 之所以是它们，靠的是第 2、3 层，不是第 1 层。

| 层 | 是什么 | 例子 | 现在的状态 |
|---|---|---|---|
| **1 内容开放** | 加道具/敌人/房间 = 写数据 | `content/enemy/*.toml` | ✅ 已做，且是整套里最扎实的部分 |
| **2 行为开放** | 加新玩法 = 写脚本，不重编译 | GMod 的 Lua 插件 | ✅ 已做：钩子契约 + mod 目录 + 授权闸门 + **L4 自定义组件 / 系统**（ADR 0007/0008/0011） |
| **3 外观开放** | 换模型 = 覆盖文件 | MC 资源包 | ✅ **静态模型覆盖已打通**（ADR 0012）：`mods/<id>/assets/meshes/<网格 id>.gltf\|glb` 盖掉内置几何，`data` 级默认放行；**贴图 / 骨骼动画仍待做** |

第 2 层的边界要说清楚：L3 能挂事件、能改返回值、能用 `api` 的动词改变世界；
L4 再往上一层 —— mod 能自带新组件（`component_spec`）和新系统（`system`），
在固定节拍上读写自己声明的字段，但**拿不到节点、`Transform3D`、组件对象**，
自定义状态也不进存档。见 ADR 0005（表格是历史快照）与
[ADR 0011](decisions/0011-l4-extension-container.md)。

第 3 层同理：现在只覆盖**静态网格**（`.gltf` / `.glb`），而且只覆盖契约里已有的
mesh id；贴图、蒙皮、骨骼动画、按配色换贴图都还没做，也不能靠放文件新增一个网格 id。
见 [ADR 0012](decisions/0012-asset-override.md)。

### 已被推翻的假设（别再犯）

- ~~HTML/WebGL 可以交付~~ → "我做的不是网页小游戏"。
- ~~不需要可视化编辑器，所以自研最划算~~ → 只算了编辑器，没算引擎的其余 80%。
- ~~自动巡航相机可以做性能对照~~ → 相机走到角落，可见数失真，结论是错的。
- ~~题材可以后定，结构不受影响~~ → **错。题材的答案是"沙盒"，它直接改写了性能优先级。**

## 二、这个答案推翻的最重要一件事：性能优先级

沙盒游戏的真实负载不是"十万个静态实例"，而是：

- **几百到几千个动态刚体**（物理积分、碰撞检测，单线程主循环）
- **玩家随时建造/删除**，负载是**突发的**，不是事先排好的
- **多人同步**（如果做），每个动态体都要发位置

我们前几天花在 draw call、分块、合批上的功夫，对这个游戏**几乎白费**——因为它的瓶颈是物理和网络，不是提交层。10 万个静态实例是错的负载；对的是几百个能被扔来扔去的箱子。

还留下的两样东西，而且确实有用：

1. **分块 / 激活半径**：沙盒世界也会大，远处的东西还是要冻结。
2. **"预算由系统强制"这个思想**：从"光源上限 8 盏"变成"物理体上限 / 建造物上限 / 每 tick 碰撞对上限"。

一句话：**技术验证的结论没错，但它验证的是另一个游戏。**

> **2026-11-20 实测补充**（第十三轮，ADR 0013）：在预算上限（119 个刚体、96 件是
> 会 AI 的怪）时，**脚本侧**才是能数得清的那部分 —— 系统步进 2.7~3.1 ms/拍、
> 剔除 0.83 ms；而物理的耗时在这台机器上量不准（无头 `TIME_PHYSICS_PROCESS`
> 空场景也报 1.3 ms，与墙上帧时对不上）。所以"瓶颈是物理"这个判断**还没被验证**，
> 已知的是脚本侧随刚体数线性增长，且它现在是可测的。

## 三、引擎：Godot 现在是唯一合理的选择

不是因为性能，而是因为 GMod/MC 需要的那四样东西它都内置：

| 平台需求 | Godot 内置 | 说明 |
|---|---|---|
| 资源覆盖（MC 资源包） | `ProjectSettings.load_resource_pack()` | 运行时加载 .pck，路径优先级覆盖原资源。**这就是 MC 资源包的实现** |
| 模组加代码（GMod 插件） | 运行时 `load()` 脚本 | 同上，从 mod 包加载 .gd 并实例化 |
| 沙盒物理 | Jolt / RigidBody3D | 抓取、堆叠、扔出去 |
| 多人（后做） | ENet 高层多人 API | 不用自己写序列化 |
| 公开发布 | 导出 Linux/Windows 单包 | 60~80MB，双击即跑 |

自研要补的是：脚本层、资源覆盖、物理、网络、打包。**任何一项都是一年起。**
在 agent 驱动的开发下更糟：私有框架每次新会话都要重新理解，引擎的 API 在训练数据里。

## 四、产品定义（建议，先接受这个，再谈扩展）

不要试图做 GMod。GMod 是建在 Source 引擎上的，而 Source 是上百人年的产物。
**能做、且已经足够发布的东西是：**

> **一个第一人称物理沙盒，核心三件事：**
> 1. 抓、放、堆、扔物体（物理手感是全部乐趣的来源）
> 2. 生成菜单（所有可选物都来自数据，因此可被 mod 扩展）
> 3. 放一个文件夹进去就能加载 mod（内容 + 脚本 + 资源覆盖）

和 GMod 的差距主要在**内容量**和**网络**，不在架构。这是一个可以逐步长大的产品，
不是"做不完就什么都没有"的项目。

**先做单人。** 理由：网络会把每个系统的复杂度乘 2，而在核心玩法（抓和扔）没定型前
做同步，等于把不确定性复制一份。多人放在公开 alpha 之后，作为独立阶段。

## 五、阶段：每段 1~2 周，随时可以停

原则：**任何一段结束时，都能打包发给朋友玩 5 分钟。** 兴趣驱动的项目最怕长期没反馈。

| 阶段 | 产出 | 验收标准 | 状态 |
|---|---|---|---|
| **P0 底座**（3~5 天） | Godot 工程 + 内容层迁入 | `godot --headless` 打印出内容条数、网格数、生成实例数，与 `pack.json` 一致 | ✅ 完成 |
| **P1 手感**（1~2 周） | 走、跳、碰撞、**抓取与扔出** | 拿起一个箱子，扔出去，它撞墙弹开，能站上去 | ✅ 完成 |
| **P2 生成**（1 周） | 物品栏 + 生成菜单 | 从菜单里点一个，物体出现在手里 | ✅ 完成（`Tab` 菜单 + 背包 + 右键拾取 + 堆叠上限 + 价值 + 准星，全部数据驱动） |
| ~~P3 开放~~ | mod 目录 + 运行时加载 + 热重载 | 往 `mods/` 扔一个文件夹，重启就多了一批内容 | ✅ 提前完成（原计划排在生成之后，但因为抓取要长在钩子上，先做了） |
| **P4 外观**（1 周） | 资源覆盖包 | 往 `assets/meshes/` 放一份 glTF，游戏里那个网格就换了，不改任何代码 | ✅ **静态模型覆盖已打通**（ADR 0012，第 11 步探针）；**贴图 / 骨骼动画仍待做** |
| ~~P5 脚本~~ | mod 能加行为 | 一个 mod 脚本让箱子被扔时爆炸 | ✅ 提前完成（同 P3） |
| **P6 公开**（2 周） | Linux + Windows 包、itch.io 页面 | 不装任何东西的人能玩到 5 分钟 | 未开始 |
| P7 多人（可选，单独评估） | — | — | 未开始 |

**顺序被改过一次，理由要记住**：原计划是"先做生成菜单，再做 mod 开放"。
实际是先做开放。因为 P1 的抓取要动手了，而抓取如果不长在钩子上，
就会变成引擎硬编码 —— mod 只能看不能改，之后补钩子等于把抓取重写一遍。
**这是这个项目里唯一一个"顺序错了必须返工"的地方**（ADR 0007）。

存档不在原计划里，是补上的：沙盒没有存档就不是沙盒，
"关了再开东西就没了"会让人立刻觉得这是个玩具（ADR 0008）。

P0 之所以只要 3~5 天：现有 `content.pack.json` 是纯数据，Godot 侧只需要读它。

## 六、为 agent 维护设计的四条铁律

1. **栈必须是主流的。** 主流栈的坑都在训练数据里；私有框架的每个问题都是盲猜。
2. **内容必须是数据。** 出错时影响面被限制在单个文件，可以单文件回滚。
3. **每个里程碑必须能一条命令验收。** 不能验收 = 没做完。数字比人眼可靠。
4. **决策写进仓库。** 每次会话都失忆。这份文档 + `architecture.md` + `docs/decisions/`
   就是交接材料。

---

## 七、明确不做

- **不追求极致的 draw call**。沙盒的瓶颈是物理，不是提交。
- **不做可视化关卡编辑器**。用生成菜单 + 数据文件替代。
- **不做实时阴影 / GI / SSAO**。风格化低模 + 顶点色 + 烘焙光。
- **不在核心手感定型前做多人。**
- **不做移动端。**
- **不做"什么都能加"的无限承诺**。先做到"内容、外观、行为"三层都能被第三方扩展，
  这就是 GMod 的全部秘密，剩下的靠社区。

---

## 八、路线重排：先做 agent 创作闭环（2026-11-14）

用户明确：**近期不指望别人做 mod，更希望 agent 能很方便地修改任意内容。**
所以前一版"陌生作者 → 社区 → 生态"的优先级往后放，近期只服务一个真实作者：
下一个会话里的 agent。它不是假想用户，而是这个项目现在最主要的开发与内容生产方式。

### 产品的差异化假设

Tessera 不跟 GMod / MC 比内容积累，也不跟大型商业游戏比美术。
它最值得验证的差异是：**契约机器可读、mod 是目录、编译器会拒绝、探针能验收，
因此 agent 可以把一句玩法需求可靠地变成能玩的内容。**
这是待验证的产品假设，不许提前写成"已经有生态"。

### "任意内容"的边界

- 可以直接扩展：道具、敌人、房间、数值、生成菜单、外观、事件行为、固定节拍规则。
- 需要通用引擎能力时：先由一个真实玩法证明需求，再扩宽契约或 facade，不能加特判。
- 不在承诺内：随意改物理求解、渲染管线、网络同步。这些仍是独立 ADR 的引擎工作。
- **开放不等于把节点树交给 agent。** 那只会让每次修改都绑死内部实现，长期反而更难改。

### 接下来的阶段门

| 顺序 | 产出 | 过关标准 |
|---|---|---|
| **A1 agent 真实修改闭环** | 一个可组合的物理机关 / 交互示例 + 对应探针 | ✅ **第一件已完成**：`mods/kinetics/` 只走公开契约与 facade，就用固定节拍 + `api.impulse` 做出会推开任意刚体的脉冲排斥器；第 12 步验冲量 / 方向 / 冷却 / 通用目标选择。按钮、门、静态交互物仍是后续真实需求 |
| **A2 修改不会丢成果** | mod 状态持久化与版本边界 | 存档 / 读档后规则状态还在；卸载或升级有明确行为，不静默丢数据 |
| **A3 发布链路提前去险** | Linux / Windows 导出包 | 脚本、L4 系统、资源覆盖、外部 glTF 不只编辑器二进制可用 |
| **A4 统一视觉与可玩 alpha** | 一套统一 CC0 风格化资产 + 基础动画 + 单人包 | 新人不看代码能玩一段完整沙盒循环；官方资产也走资源覆盖通道 |
| **A5 再评估社区与多人** | 由真实需求决定 | 没有使用需求就不做商城、创意工坊、依赖管理或网络层 |

多 spawner、存档槽位、贴图系统的完整性都不是当前最优先；它们等真实修改需要时再做。
每个阶段仍遵守同一条：**停下时必须能玩，且 `./check.sh` 能证明。**
