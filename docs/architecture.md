# 开放架构

一句话定义：

> **开放架构 = 有限个扩展点 + 数据与代码彻底分离 + 边界处强制校验。**
>
> 不是"什么都能改"，而是"知道该在哪改，改错时立刻知道"。

这个仓库里的每个文件都在执行这条定义。下面按"你能改什么 / 你不能改什么 / 为什么"来讲。

---

## 1. 四层结构

| 层 | 目录 | 开放程度 | 谁改 | 改错会怎样 |
|---|---|---|---|---|
| 契约层 | `common/registry.py` | 只允许**加**，不允许改语义 | 你 | 全局校验失效，所有内容都可能悄悄错 |
| 内容层 | `content/`、`mods/` | **全开放** | 任何人，包括不写代码的人 | 编译期报错，坏内容进不了运行时 |
| 系统层 | `runtime/systems.py` | 开放，但受声明约束 | 你 | 启动时被 `check_system_order()` 拦下 |
| 引擎通道 | `runtime/ecs.py`、`runtime/render.py` | **关闭** | 只有你，且要慎重 | 性能失控，且没有任何校验能救你 |

分界线只有一条判据：

> **一段代码如果决定了"每帧要提交多少东西"，它就属于引擎通道，不开放。**

因为帧率是全局资源，任何单条内容都不该有权限动它。这就是下面第 5 节"光源预算"那段代码存在的理由。

---

## 2. 五个扩展点

不多不少，就这五个。想加第六个之前先问自己：能不能用现有的五个凑出来。

| # | 想做什么 | 改哪里 | 数据层立刻能用的东西 |
|---|---|---|---|
| 1 | 加一种**属性/状态**（中毒、饥饿、护甲） | `registry.component("poison", ...)` | `[components.poison] dps = 0.5` |
| 2 | 加一种**行为**（逃跑、召唤、巡逻路线） | `registry.BRAINS` 里加 id | `brain = "flee"` |
| 3 | 加一种**网格** | `registry.MESHES` 里加 id 和三角形数 | `mesh = "goblin_lowpoly"` |
| 4 | 加一种**内容形态**（配方、对话、任务） | `registry.kind("recipe", ...)` + 一个解析分支 | 一种新的 `.toml` 文件 |
| 5 | 加一种**机制**（天气、仇恨衰减、昼夜） | `@system(...)` 一个函数 | 不需要动数据 |

关键在于**一次声明，全链路生效**：

```python
# common/registry.py 里加这 6 行
component(
    "poison",
    "中毒。每帧扣血，可叠加。",
    dps=Field("float", 0.5, 0.0, 100.0),
    stacks=Field("int", 1, 1, 10),
)
```

加完之后，**已经写好的**校验器、`components.md` 文档生成、未来的编辑器属性面板、`mods` 的 patch 通配覆盖，全部自动支持 `poison`。你不需要通知任何人。这就是"开放"和"留个口子"的区别。

然后系统层消费它：

```python
@system("poison_tick", priority=110, reads=("poison", "health"), writes=("health"))
def poison_tick(world, active, dt):
    for e in active:
        p = e.comps.get("poison")
        if p is None:
            continue
        h = e.comps["health"]
        h["hp"] = max(0, h["hp"] - int(p["dps"] * p["stacks"] * dt))
```

两处改动，数据层就有了一个新玩法。**没有第三处。**

## 3. 内容格式

一个内容文件 = 一个实体。文件名就是它的身份（也可以用 `id` 显式指定）。

```toml
api_version = 1                 # 必填。格式变了靠它做迁移
kind = "archetype"              # 必填。决定它是"世界里摆的东西"还是"背包里的东西"
id = "enemy/bone_walker"        # 可选。不写就用相对路径
extends = "enemy/base_undead"   # 可选。父模板
name = "骨行者"
tags = ["melee", "undead"]

[components.health]
max = 45

[components.move]
speed = 1.8
```

三条规则：

1. **`extends` 是字段级合并**，不是整体覆盖。子模板只写自己关心的字段，其余从父模板继承。
2. **`patch` 是运行前的覆写**，用通配符指定目标，`set` / `mul` / `add` 三种操作：
   ```toml
   kind = "patch"
   target = "enemy/*"
   [components.health]
   max = { mul = 1.6 }
   ```
3. **patch 不沿继承链传播**。它作用在"解析完继承之后的最终实体"上。想影响一整个族群就写通配符。

`api_version` 的意义在于：等你哪天把 `max` 改名成 `max_hp`，所有旧内容文件会在编译期被拦住，而不是在某人玩了 20 小时后血量变成 0。

### 加载顺序与 mod

```
--content content --content mods
           ↑ 先加载      ↑ 后加载，可以 patch 前面的
```

顺序是**唯一**的覆盖机制。后加载的内容可以 patch 先加载的，反过来不行。这条规则简单到不需要文档，但它让"官方内容 / 官方 DLC / 社区 mod"三者天然有优先级。

同一目录里两个文件声明同一个 `id` 会直接报错——想覆写就老老实实写 `kind = "patch"`。**宁可报错，也不要让"谁覆盖了谁"变成玄学。**

## 4. 校验：开放架构的地基

没有校验的开放架构等于没有架构。这个仓库的规矩是：

> **校验失败就不产出 pack。坏的构建产物永远到不了运行时。**

实际输出长这样：

```
编译失败，4 个问题：

  ✗ content/a.toml: `a` 使用了未注册的组件 `healht`（已注册：ai, collider, health, ...）
  ✗ content/b.toml: `b.ai.brain` `berserk` 不在允许值 ['idle', 'patrol', 'charger', 'ambusher'] 中
  ✗ content/b.toml: `b.health.max` 不能小于 1（当前 0）
  ✗ content/c.toml: extends 指向不存在的 id `enemy/does_not_exist`
```

四类检查，缺一不可：

| 检查 | 拦住的真实事故 |
|---|---|
| 组件名 / 字段名存在 | 拼写错误，运行时才崩或者静默失效 |
| 类型 + 范围 + 枚举 | 血量填成 0，仇恨半径填成 300 米 |
| 引用完整性 | 继承了一个被删掉的模板、生成器指向不存在的怪 |
| 继承环 | A extends B, B extends A，无限递归 |

再加一条对"改"极其重要的：**热重载会告诉你哪个字段从多少变成了多少**。

```
~ 修改 enemy/bone_walker
     health.max: 72 -> 83
     move.speed: 1.8 -> 2.6
```

（显示的是**乘过 patch 之后的最终值**，也就是运行时真正看到的值。）

## 5. 引擎通道：预算由系统强制，不由内容自觉

这一节是整个架构里最容易被忽略、但决定游戏能不能流畅跑的部分。

内容层可以无限扩张，但帧预算必须封闭。所以引擎通道有三处**不由内容决定**的强制行为：

### 视锥 + 距离 + 区块三级剔除

```python
if math.hypot(bx, bz) > self.far + CHUNK * 1.5:
    continue        # 整块不参与后面所有计算
```

先按区块粗筛（一次距离计算干掉几十个实体），再对剩下的一批做逐实体判定。顺序反了，性能就差一个量级。

### 合批：一物一次提交 → 按 (网格, 配色) 一次提交

```python
key = (mesh, palette) if instancing else (mesh, palette, e.eid)
```

配色是**材质参数**，不是材质。同一棵树换 8 种叶子颜色，仍然是 1 个 draw call。

### 光源预算：最近的 8 盏

```python
def limit_lights(entities, cx, cz, budget=8):
    ...
    lit.sort(key=lambda e: (e.x - cx) ** 2 + (e.z - cz) ** 2)
    for e in lit[budget:]:
        e.comps["light"]["_on"] = False   # 超预算的灯熄灭
```

这段代码是我在跑完对照实验后**才加的**。原来 30000 个内容里，可见的发光体有 45 个，全部点亮直接超预算——而内容层完全看不出来自己做错了什么。现在内容想加多少发光怪都行，引擎每帧只点亮最近的 8 盏。

这就是"内容开放、预算封闭"的具体形态：**设计上不禁止，但越界会被系统收走。**

### 预算档位：核显和独显不是一个数量级

`runtime/main.py --tier` 两档，默认核显。原因是**核显和 CPU 共享内存带宽**，填充率和显存吞吐是卡住它的东西，不是顶点数：

| 项目 | `igpu`（默认） | `discrete` |
|---|---|---|
| draw call | 200 | 800 |
| 动态光源 | 4 | 12 |
| 三角形 | 600k | 2.5M |
| 激活实体 | 400 | 800 |

注意核显档把**动态光源压到 4**。这一条比三角形更重要：现代核显画 60 万三角形很轻松，但每多一盏实时光源，片元都要多算一遍，而它算的像素和你屏幕像素一样多。屏幕分辨率才是真正的乘数——所以核显上宁可降内部分辨率再放大，也别加灯。

## 6. 实测

同一份内容，同样 90 帧，只改内容的数量和摆法。

**表一：内容从 100 条涨到 30000 条（300 倍），世界跟着放大，密度不变**

| 实体数 | 驻留区块 | 驻留实体 | 激活 | 可见 | draw call | 三角形 | 估算 ms |
|---|---|---|---|---|---|---|---|
| 100 | 4 | 100 | 28 | 6 | 2 | 2.0k | 4.43 |
| 1000 | 30 | 836 | 66 | 64 | 3 | 22.8k | 4.58 |
| 3000 | 41 | 1164 | 59 | 150 | 3 | 53.4k | 4.59 |
| 10000 | 53 | 1571 | 53 | 171 | 3 | 58.2k | 4.57 |
| 30000 | 63 | 1952 | 58 | 174 | 3 | 60.3k | 4.59 |

**内容翻 300 倍，帧开销涨 3.6%。** 因为涨的只是"硬盘上多了多少东西"，不是"这一帧要画多少东西"。

**表二：同样 30000 条内容，四种摆法**

| 摆法 | 可见 | draw call | 三角形 | 激活 | 估算 ms | 约 fps |
|---|---|---|---|---|---|---|
| 世界放大 · 密度不变 | 174 | 3 | 60.3k | 58 | **4.6** | 218 |
| 关掉实例化 | 174 | 174 | 60.3k | 58 | 7.7 | 130 |
| 全挤在 200×200 里 | 1789 | 3 | 617.2k | 2017 | 11.0 | 91 |
| 挤在一起 + 关实例化 | 1789 | 1789 | 617.2k | 2017 | **43.2** | 23 |

同样是 30000 条内容，最好的摆法和最坏的摆法差 **9.4 倍**。

结论不是"内容要少"，而是：**内容多必须表现为世界大，不能表现为密度高。** 一旦密度上去，模拟层（2017 个激活实体 × 3µs）和提交层（1789 个 draw call）会同时爆掉，而这两样都是合批和分块救不回来的。

成本模型是可改的估算，绝对值不必当真；要看的是同一模型下不同摆法之间的**比值**。

## 7. 世界分块

`CHUNK = 40` 米一个块。每帧只处理相机附近 9×9 个块，全量内容按块分布。

两个集合必须分开：

- **可见**：在视锥内、在视距内。要提交渲染。
- **激活**：在激活半径内（30 米）。要跑逻辑。

```
可见但不激活  = 远处看得到，逻辑冻结   ← 省钱的关键状态
激活但不可见  = 就在你背后，逻辑还在跑 ← 音效和威胁感需要它
```

把这两个混成一个"在不在附近"的判断，是最常见的架构错误之一：混了之后要么远处的东西也在跑 AI（费 CPU），要么背后的怪不会绕过来打你（玩法坏了）。

## 8. 确定性

开放架构有个隐藏前提：**同样的内容必须产生同样的行为**，否则"改了 A 导致 B 异常"永远查不出来。

三条保证：

1. **固定步长**模拟（30Hz），渲染帧率再高也不影响逻辑。
2. **每个实体独立种子**：`seed = world_seed * 1000003 + entity_id`。不用全局随机数生成器——那样加一个实体就会改变其他所有实体的随机序列。
3. **系统顺序由 priority 决定，冲突直接拒绝启动**：
   ```
   写入冲突检查：通过
   ```
   如果有两个系统都写 `health` 且优先级相同，运行时会拒绝启动，而不是"谁先跑看运气"。

## 9. 反模式

开放架构失败的方式不多，就这几种：

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| `if archetype == "bone_walker"` 这种按 id 分支 | 每加一种内容就要改代码，架构名存实亡 | 用组件表达差异 |
| 系统之间直接互相调用 | 执行顺序变成隐式依赖，改一处崩一片 | 只通过组件交流 |
| 内容文件里写脚本 / 表达式 | 校验失效，mod 变成任意代码执行 | 只允许引用已注册的 id |
| 给引擎通道开扩展点 | 帧率无法保证，且没人能定位是谁搞坏的 | 引擎通道保持封闭 |
| 在 `world.entities` 里全量遍历 | 内容越多越卡，这条是表二第三行的成因 | 走空间网格 + 激活列表 |

## 10. 看一眼：真的能走

同一个渲染核心，两种上下文，两个可执行文件：

```
game/src/renderer.hpp  唯一一份绘制代码（天空 / 地面 / 接触阴影 / 实例化内容 / 准星）
game/src/world.hpp     分块 → 激活 → 视锥 → 合批，与 ecs.py/render.py 逐行对应
game/src/player.hpp    玩家控制器：键盘 → 相机（窗口版与回放版共用）
game/src/window.hpp    X11 + GLX 窗口、键鼠状态、垂直同步
game/src/game.cpp      窗口版：游戏循环 + 标题栏 HUD + 截图
game/src/shot.cpp      离屏版：EGL 上下文、出图、--replay 逐帧导出
game/src/mesh.hpp      程序化低模；三角形数的唯一真实来源
game/src/pack.hpp      读 content.pack.bin，零解析
```

```bash
./game/build/game --pack build/content.pack.bin --n 100000     # 能玩的，WASD + 鼠标
./game/build/shot --pack build/content.pack.bin --n 30000 --at "100,100,0" --out build/a.ppm
```

两者走的是**完全相同的 GL 调用路径**（`glDrawArraysInstanced`），区别只在
"画到窗口的 back buffer"还是"画到 pbuffer 再读回来"。所以窗口里看到的画面、
`--replay` 导出的录像、`--out` 出的图，是同一个东西。

**为什么输入用 XQueryKeymap 轮询而不是事件队列**：按住 W 时 X 会成对地发
KeyRelease/KeyPress（自动重复），自己维护按键状态机要额外处理这个；直接每帧问
服务器"现在哪些键是按下的"就没有这个问题。鼠标同理，但要用**上一次 warp 的位置**
当参照而不是窗口中心 —— 窗口一被窗口管理器改尺寸，用中心算就会每帧凭空造出
十几像素的偏移，几十帧后视线已经歪到天上去了。我在这上面吃过一次亏。

实测（1100×620，钉死相机，多次运行取最小值）：

| 场景 | 可见 | draw call | 三角形 | ms/帧 |
|---|---|---|---|---|
| 3 万条，正常摆法 | 174 | **3** | 10212 | ≈26 |
| 3 万条，挤在 200×200 | 5220 | **3** | 313668 | ≈131 |
| 3 万条，密集 + 关合批（400×240） | 5220 | **5220** | 313668 | 84 |
| 3 万条，密集 + 开合批（400×240） | 5220 | **3** | 313668 | 70 |

密集场景里可见的发光体有 1306 个，实际只点亮 8 盏 —— 这就是"预算由系统强制"的样子。

诚实的一条：**在 llvmpipe 上合批只值 20%**。mesa 的软件光栅每次提交几乎不要钱，
所以 5220 次提交 84ms、3 次提交 70ms。真显卡的 GL 驱动每次提交都要做状态校验，
5000 次通常贵得多，但这个环境测不出来。这条结论要等你自己的机器验。

## 11. 为什么选自研而不是引擎

结论：**C++17 + GLX + OpenGL 3.3 core，零第三方依赖，产物一个可执行文件。**

判断依据不是"自研性能更高"，而是下面这条推论：

> **内容即数据 → 不需要可视化编辑器 → 自研最大的一项成本消失了。**

通常自研 3D 的成本结构是「渲染器 : 编辑器 : 编辑器配套 = 1 : 3 : 3」，所以大家用引擎。
但这套架构里关卡就是 TOML、道具就是 TOML、怪就是 TOML，编译期已经校验过一遍，
**根本没有"摆场景"这个动作需要可视化**。于是剩下的只有渲染器本身，而那部分正好是
"C/C++ 熟手 + 风格化低模"最划算的活儿。

性能排序（同等内容量下）：

| | 每帧固定开销 | 提交开销 | 启动 | 体积 | 能改到多深 |
|---|---|---|---|---|---|
| 自研 | ~0 | 最低 | <50ms | ~2MB | 全部 |
| Bevy | 调度器 | 低 | ~100ms | ~10MB | 到 Bevy 内部 |
| Godot 4 | 场景树 + 脚本 VM | 中（有自己的抽象层） | 300ms+ | ~80MB | 到 GDExtension 为止 |

代价要说清楚：光照/阴影/后处理全要自己写；头两周画面只有色块；
移动端要另外做打包链路。风格化路线（烘焙光 + 顶点色 + 低模）正好是这个代价的甜区。

## 12. 如果以后要换引擎

内容和契约这两层是引擎无关的，`pack.bin` 是纯数据。所以真要换，代价集中在渲染器：

| 这里的 | Godot 4 | Bevy |
|---|---|---|
| `pack.hpp` | 自定义 `Resource` 读同一份 bin | `Asset` + `serde` |
| `world.hpp` 的漏斗 | 每块一个 `MultiMeshInstance3D`，切 `visible` | 按块分组 Entity + `Visibility` |
| `batch()` | `MultiMesh` | 引擎自动 instancing |
| `pick_lights` | `RenderingServer` 的灯上限 + shader 内循环上限 | 光源数量限制组件 |
| `@system` 函数 | `_process` 里遍历 | 原生 system 塞进 `Schedule` |

**内容和契约是资产，渲染器是可替换的执行层。**
