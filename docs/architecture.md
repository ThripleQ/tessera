# 开放架构

一句话定义：

> **开放架构 = 有限个扩展点 + 数据与代码彻底分离 + 边界处强制校验。**
>
> 不是"什么都能改"，而是"知道该在哪改，改错时立刻知道"。

---

## 0. 先看这个：状态标记

这份文档里每条陈述都带一个标记。**没有标记的陈述就是设计，不是事实。**

| 标记 | 含义 |
|---|---|
| ✅ | 已实现，且 `./check.sh` 每次都会验证 |
| 🧪 | 通道已验证可行（有实测记录），功能尚未实现 |
| 📐 | 设计意图，未验证。**不要当成已具备的能力引用** |

为什么先声明这个：这份文档某一版有一半在描述一个已经归档的自研渲染器
（`runtime/ecs.py`、`game/src/*.hpp`），下一个 agent 照着读会读到一套不存在的架构。
**比缺文档更危险的是过期文档，因为它看起来是权威的。**

## 1. 分层

| 层 | 目录 | 开放程度 | 谁改 | 改错会怎样 |
|---|---|---|---|---|
| 契约层 | `contract/registry.py` | 只允许**加**，不许改语义 | 你 | 全局校验失效，所有内容都可能悄悄错 |
| 内容层 | `content/` | **全开放** | 任何人，包括不写代码的人 | 编译期报错，坏内容进不了运行时（✅） |
| mod 层 | `mods/`、`user://mods/` | **全开放，可独立发布** | 任何人 | 编译期报错；带脚本需授权（✅） |
| 引擎层 | `game/` | 开放，但受 `lint_arch.py` 约束 | 你 | `check.sh` 第 3 步变红（✅） |
| 归档层 | `legacy/` | **冻结** | 没有人 | 不许往里加代码 |

分界线只有一条判据：

> **一段代码如果决定了"每帧要提交多少东西"，它就属于引擎底层，不开放。**

因为帧率是全局资源，任何单条内容、任何一个 mod 都不该有权限动它。
这条在沙盒里仍然成立，只是"每帧多少东西"从 draw call 变成了**物理体数量和碰撞对数**。

## 2. 五个扩展点

不多不少，就这五个。想加第六个之前先问：能不能用现有的五个凑出来。

| # | 想做什么 | 改哪里 | 数据层立刻能用的东西 |
|---|---|---|---|
| 1 | 加一种**属性/状态**（中毒、饥饿、护甲） | `registry.component("poison", ...)` | `[components.poison] dps = 0.5` |
| 2 | 加一种**行为**（逃跑、召唤、巡逻路线） | `registry.BRAINS` 里加 id | `brain = "flee"` |
| 3 | 加一种**网格** | `registry.MESHES` 里加 id | `mesh = "goblin_lowpoly"` |
| 4 | 加一种**内容形态**（配方、对话、任务） | `registry.kind("recipe", ...)` + 解析分支 | 一种新的 `.toml` 文件 |
| 5 | 加一种**机制**（天气、昼夜、仇恨衰减） | 引擎层一个系统；或者 mod 里 `component_spec` + `system` | 后者连数据形状一起由 mod 声明 |

关键在于**一次声明，全链路生效**：加完 `poison`，已经写好的校验器、文档生成、
未来的属性面板、mod 的 patch 通配覆盖，全部自动支持它。你不需要通知任何人。

这就是"开放"和"留个口子"的区别。

**L4 之后第 5 项不再只属于引擎**（✅ ADR 0011）：一个 mod 可以用
`kind="component_spec"` 声明新组件的字段，用 `kind="system"` 声明一条固定节拍规则，
再由引擎统一编译、校验、排序、调度。引擎仍然不认识 mod 的内容，只认识
「怎么装载别人声明的规则」。内容不是靠往 `content/` 里堆，而是靠这条通道长出来。

## 3. 内容格式

一个内容文件 = 一个实体。文件名就是它的身份。

```toml
api_version = 1                 # 必填。格式变了靠它做迁移
kind = "archetype"              # 必填
extends = "enemy/base_undead"   # 可选。父模板
name = "骨行者"
tags = ["melee", "undead"]
abstract = false                # 可选。true = 只能被 extends，不能单独存在

[components.health]
max = 45

[components.move]
speed = 1.8
```

四条规则：

1. **`extends` 是字段级合并**，不是整体覆盖。子模板只写差异。
2. **`patch` 是运行前的覆写**，用通配符指定目标，`set` / `mul` / `add` 三种操作。
3. **patch 不沿继承链传播**。它作用在"解析完继承之后的最终实体"上。
4. **`abstract` 不继承**。给基类标上它，子类照旧是具体内容。

同一批输入里两个文件声明同一个 `id` 直接报错。
**宁可报错，也不要让"谁覆盖了谁"变成玄学。**

### `abstract`：给"模板"一个机器可读的标记（✅）

`abstract = true` 的实体不进生成菜单、不能被房间的 `spawner` 指向、不进二进制包。
一句话：**它只能被 extends。**

反过来问一句：为什么不在 `tags` 里塞一根 `"abstract"` 字符串？
因为 tags 是**内容之间**的约定（mod 可以往里加任何东西），而"能不能出现在世界里"
是**引擎的行为**。把引擎行为挂在一根内容字符串上，写错一个字母的后果是
「基类被当成实体摆进世界」—— 而那种错误看起来完全正常，没人会去查。

这也是这个项目反复踩到的同一个坑（见 §9 最后两行）：
**注释里写的规则，如果代码没做，那规则就不存在。** 在 `abstract` 之前，
`base_undead.toml` 的 `doc` 里写着"它本身不会被摆进世界"，而生成菜单的第一项就是它。

`abstract` 不继承是这一条里最容易搞反的地方：如果跟着 `extends` 传下去，
给基类标一个 abstract 会连带把**所有子类**变成模板，房间里那一整类东西静默消失。
`docs` 与编译器自测（`contentc --selftest`）各盯一遍。

### 三种来源，两个阶段（✅ 见 ADR 0008）

```
官方内容 content/            → 编译期 → game/content.pack.json
mods/<id>/                   → 各自编译 → mods/<id>/content.pack.json
user://mods/<id>/            → 各自编译 → 同上（玩家装的）
                                        ↓ 运行时
                                 按授权顺序合并进内存里的 pack
```

**覆盖只发生在运行时，按 mod id 的字典序**，不按文件系统顺序。
确定的顺序是"同一个世界在任何机器上长得一样"的前提。

一个 mod 的产物里**只有它改变了的东西**：编译 `kind="patch"` 的内容时，
编译器会把基线也编译一遍再取差异。所以产物是"我改变了什么"，
不是"我抄了一份世界"——这也是多个 mod 能叠加的原因。

## 4. 校验：开放架构的地基

> **校验失败就不产出 pack。坏的构建产物永远到不了运行时。**（✅）

四类检查，缺一不可：组件名/字段名存在、类型+范围+枚举、引用完整性、继承环。
再加一条对"改"极其重要的：**热重载会告诉你哪个字段从多少变成多少**，显示的是乘过
patch 之后的最终值。

顶层字段也在校验范围内（`TOP_FIELDS`）：字段名拼错（`abstact`）和类型写错
（`abstract = "true"`）都当场报错。字段名是内容侧最高的错误率来源，而这类拼错
**静默不生效**——它不报错，只是那条规则没起作用。

### 校验器自己也要被检查（✅）

`./check.sh` 第 1 步先跑 `contentc --selftest`：拿五个**故意写坏**的小内容，
确认编译器真的会拒绝（`abstract` 不继承 / 抽象不能被 spawner 指向 / 顶层字段拼错 /
顶层字段类型错 / patch 不能改 abstract）。

理由和 `lint_arch.py --selftest` 一模一样：**一个从来没拒绝过东西的校验器，
和不存在没有区别，而且更危险，因为它看起来是绿的。** 这条自测写完当天就抓到了一次
"摘掉 `abstract` 不继承的逻辑，编译器依然全部接受"。

### 契约怎么到达引擎（✅ 见 ADR 0002）

契约只有一份：`contract/registry.py`。编译期导出成 `pack.schema`，随包一起走。

- `pack.gd` 把 `schema` 当**硬要求**，缺了（包括缺 L4 扩展规则段）就拒绝加载
- 自检校验 `内容用到的组件 ⊆ 契约声明的组件`
- **合并 mod 之前再校验一遍**：编译期校验是*作者的*编译器跑的，
  而 mod 产物是外部文件、可以被手改。契约是唯一的信任根，它在引擎这一侧
- `schema.components` 里既有 `origin="builtin"` 的内置组件，也有 mod 运行时
  并进来的自定义组件。同一张表意味着同一套字段类型 / 范围 / 枚举校验，
  不给「外部数据」开后门
- `schema.extensions` 带规则常量与系统声明；`pack.apply_extension()` 先整份校验
  再整份合并，冲突不许留下「组件进来了、系统没进来」的半装状态

**契约说世界能有什么，实现清单说引擎现在能处理什么，两者之差就是待办。**

当前：**13 个内置组件**，基础内容用到 12 个，引擎真正**读**了 9 个
（`model` 的几何与配色、`collider` 的碰撞与刚体、`spawner` 的房间填充、`room` 的尺寸、
`pickup` 的堆叠上限与价值、`move` 的速度与游荡、`ai` 的脑回路与仇恨半径、
`health` 的血量与回血、`loot` 的掉落表与概率）。其余 4 个（`light` / `interaction` /
`wieldable` / `transform`）还是一行数据。这个缺口不会自己消失。
**L4 的自定义组件不算在这 13 个里**：它由声明它的 mod 系统自己读，
`mods/l4_demo` 的 `pulse` 就是那个「第一次由外部声明、被引擎按数据校验」的样品。

**系统层**（`game/scripts/systems/`）是把死数据变活的地方：`locomotion` 读
`move` + `ai` 写速度，`vitals` 读 `health` + `loot` 结算受伤 / 死亡 / 掉落。
两个系统**不许互相认识**，只通过组件交流 —— 顺序一旦成了隐式依赖，
改一下执行顺序行为就变，而且没有任何提示。
mod 系统从 priority=100 起插在同一张有序表里，见 §5 ② 与 ADR 0011。

网格侧已经全覆盖：契约 7 种，引擎实现 7 种（`world/mesh_lib.gd`）。
少一种就等于那类东西会静默地从世界里消失，所以自检里缺一个都算失败。
**三角形数是实测值**：引擎会拿契约里的数字和自己数出来的比，不一致直接失败。

## 5. 三个开放通道

产品的三层开放不是并列的，是渐进的。现状必须说清楚：

> **开放度到 L4（mod 能声明新组件与新规则），且 mod 现在可以真正"装"。**
> 六层定义与"一族而非任何游戏"的分界见 [ADR 0005](decisions/0005-openness-boundary.md)，
> L4 的边界见 [ADR 0011](decisions/0011-l4-extension-container.md)。
> **不要对外宣称"能做任何游戏"。** 钩子实现见 [ADR 0007](decisions/0007-hooks.md)，
> mod 装载见 [ADR 0008](decisions/0008-mods-and-saves.md)。

### ① 内容开放 ✅

写 TOML 就能加道具、敌人、房间。已完整可用，是整个仓库最扎实的部分。

### ② 行为开放 ✅（事件脚本 + L4 组件 / 系统）

**钩子表 + 事件总线 + mod API + 运行时装载 + 授权闸门 + 系统容器，已实现并跑通。**

一个 mod 就是一个目录：

```
mods/<id>/
  mod.toml              [mod] id / name / version / api_version / level / author
  content/*.toml        内容（脚本路径相对 mod 目录）
  scripts/*.gd          可选，level=script 才需要
  content.pack.json     产物（contentc --mod 生成，不进版本库）
```

四层结构：

```
contract/registry.py  hook(...)      声明：参数 / 返回值 / 能否否决
       ↓ 编译期导出
pack.schema.hooks                    引擎据此校验"我发的都是契约里的"
       ↓
game/scripts/hooks/bus.gd            路由 + 预算 + 权限闸门
game/scripts/hooks/api.gd            交给 mod 的唯一对象（只有动词，没有节点）
game/scripts/mods/registry.gd        发现 → 授权 → 合并
game/scripts/mods/loader.gd          运行时编译 + 绑定
       ↓
mods/<id>/scripts/*.gd               单个 handle(event, ctx, api) 入口
```

三条硬约束：**没声明的事件发不出去**、**没写进 events 的收不到**、**每帧事件数有上限**。

#### L4：mod 自带组件与规则（✅ ADR 0011）

事件脚本回答"某件事发生时做什么"，**规则**回答"每过一拍世界该怎么变"。
后者以前只能改引擎，现在是一个 mod 文件夹里的三份数据：

```
kind="component_spec"   key + fields[{type, default, min/max, enum}]
        ↓ 编译期导出 extensions.components → 运行时并入 schema.components
kind="system"           source + reads + writes + priority + period
        ↓ 同一个 loader 编译，交给 systems/runner.gd 按 (priority, id) 调度
mods/<id>/scripts/*.gd  只有一个入口 step(ctx, api)
```

`ctx`（`scripts/mods/system_api.gd`）只给四样东西：`entities()` 返回不透明 handle，
`read()` / `write()` 按该系统的读写集访问组件字段，`dt` / `frame` 是节拍信息。
写值还要过字段类型 / 范围 / 枚举；越权调用返回 false / null 并把原因放进
`last_error`，不刷引擎 ERROR。改变世界仍走 `api` 的动词（spawn / impulse / tint）。

四条边界，每条都有验收盯着：

1. **固定节拍，不是每渲染帧。** `period` 有下限，掉帧时一帧最多补一次，
   不让卡顿把规则放大成雪崩。需要逐帧手感的东西属于引擎内置系统（ADR 0011）。
2. **状态不进存档。** 自定义字段的可变值按 handle 存在内存里，
   物体消失就 `prune`。存档仍只存玩家的动作；重开一局让规则从内容默认值长回来。
3. **不许覆盖内置组件，系统优先级不许撞车。** 编译期、运行时各查一遍；
   多个 mod 的优先级一旦相同，顺序就不能靠字典遍历决定。
4. **带系统的 mod 和带事件脚本的 mod 同级。** 都是可执行代码，默认拒绝，
   `--trust=<id>` 才放行。编译器与引擎各独立算一次真实级别。

`check.sh` 第 10 步会真的造一件 mod 内容、跑三拍（`charge 0 → 0.375`）、
再试着越权读写与写错类型。只"装上了"不算开放。

不引入 Lua。GDScript 在训练数据里，Lua 绑定不在——这对"agent 长期维护"是决定性的。

**没有沙箱，这是硬事实**：mod 脚本里 `OS.execute` 的返回码是 0。所以 mod 分两级：

| 级别 | 内容 | 默认 |
|---|---|---|
| `data` | TOML + 资源，不执行代码 | 默认放行 |
| `script` | 额外带 `.gd`（事件脚本或 L4 系统），**完全权限** | **默认拒绝**，需玩家显式授权 |

两条不能妥协的判定：

1. **级别由"有没有可执行代码"决定，不由作者声明决定。**
   作者可以把带脚本 / 系统的 mod 标成 `data` 来跳过授权，编译器与引擎各自独立算一遍真实级别。
2. **授权是默认拒绝。** 没有记录 = 从没授权过。开关是 `--trust=<id>`，
   写在 `user://mods.json`，一次有效长期有效。

### ③ 外观开放 🧪

**通道已实测可行，功能未实现。** 走目录 overlay，不走 `.pck`：

```
解析路径 → 已启用 mod 目录（后加载优先） → res://assets/ → 第一个命中即生效
```

`Image.load_from_file(绝对路径)` 和 `DirAccess` 都验证通过。
**不需要打包工具链，因为资源包的本质就是文件夹**——这也是 MC 的形态。

**但要说清楚现在的真实边界**：`model.mesh` 只能取 `registry.MESHES` 里那 7 个 id，
几何在 `world/mesh_lib.gd` 里用代码拼出来。所以今天的内容能换色、能换尺寸、
能换摆放，**但换不了形状**——想加一个新形状必须改引擎。

这是"外观开放"目前最大的一个洞，也是"内容开放"看起来比实际更开放的地方：
TOML 可以随便写，可写的网格是封死的。要走到真正的外观开放，需要的是
"数据能引用外部网格文件（glb/obj）"，而不是继续往 `mesh_lib` 里堆函数。
用户已拍板：**资源可以用，且优先网上找现成的**（CC0 / 可商用免费包、
Mixamo 等现成动画），入库记来源与许可。所以 P4 的方向是
「外部 glTF 模型 + 现成骨骼动画 + 资源覆盖包 + 我们的卡通着色」，
不再自己写程序化动作系统。在那之前，别对外说"可以加任意外观"。

## 6. 世界怎么组装成画面

七层，每层只依赖上一层，改一层不牵动另一层（✅ 已实现）：

```
Pack      读 content.pack.json + schema，只回答"有什么"
  ↓
Mods      发现 / 授权 / 合并。会加内容与 L4 扩展声明，不改引擎结构
  ↓
Plan      把房间排到世界里、往房间里填内容。纯数据，不建任何节点
  ↓
WorldRoot 把计划变成节点：建块、合批、剔除、造碰撞
  ↓
Player    可操控的角色：碰撞体 + 重力 + 相机 + 手（抓 / 扔 / 收）+ 背包
  ↓
Systems   引擎系统与 mod 系统按优先级跑；mod 只拿到 handle 与组件字段
  ↓
UI        生成菜单与准星。清单来自 pack，一行内容都不硬编码
  ↓
Save      采集 / 还原玩家的改动：动态刚体 + 玩家摆的静态物 + 玩家位置
```

**Systems 不进存档**：自定义组件的可变状态是规则的中间结果，不是玩家的成果。
存档那一行只抄世界里的刚体、玩家摆的静态物、玩家位置和背包（ADR 0008 / 0011）。

**为什么 Plan 必须纯数据**：无头自检只走到 Plan。如果 Plan 里 `new` 过节点，
自检退出时就会泄漏一堆 `ObjectDB instances leaked`，真正的失败会被这些噪音淹掉。
这个坑实际踩过一次，泄漏警告把自检结论挤到了下面十几行。

**为什么"把内容变成能摆的东西"只有一处**（`Pack.item_for`）：
房间填充、mod 的 `api.spawn`、存档还原都要做这件事。三处各写一遍的话，
它们会在原点、collider 默认值、`is_dynamic` 的判定上慢慢分叉，
而分叉的表现是"存档读出来的箱子和原来那个不太一样"——没有报错，只是手感悄悄变了。

几条实现上的硬规则：

- **一室一块**。契约里 `room` 组件的原话就是"分块流式加载以它为单位"。
- **合批键是网格，不是 (网格, 配色)**。配色走 `MultiMesh` 的 instance color，
  所以同一种网格只提交一次，换多少种颜色都一样。
- **会动的东西不能进合批**（见 ADR 0006）。MultiMesh 是一个节点 N 个实例，
  而物理要求每个物体一个身份，两者结构上无法共存。所以：
  静态走合批，`collider.dynamic = true` 的走独立 `RigidBody3D`。
  当前世界：**静态 2 次提交 + 动态 14 次**，后一个数字就是物理的价格。
- **房间之间留走道，走道没有地板**，所以引擎铺一块世界底板托底。底板必须有碰撞——
  否则玩家走出房间就掉进虚空，世界边界变成死亡陷阱。
- **布局规则见 ADR 0004**：房间按 id 字典序沿 X 轴排，间隔 12 米。
  排序用 id 不用文件系统顺序，保证同一份内容在任何机器上排出同一个世界。

### 存档：只存玩家的动作（✅ 见 ADR 0008）

```
user://saves/slot0.json
  { version,
    saved_at,
    player: {pos, yaw, pitch},
    bodies: [{id, p, q, v, w}],     # 动态刚体：位置 + 朝向 + 速度
    props:  [{id, p, q}],           # 玩家摆下的静态物：只有位置和朝向
    bag:    [{id, n}] }             # 背包：只有 id 和件数，没有位置
```

**不存世界本身。** 世界是内容决定的，重跑一次就有；存档要保住的是玩家的成果。
所以没有房间、没有地面、没有房间自带的静态障碍——那些是内容的形状，改了内容就该跟着变。

这里有一条容易忽略的分界：**房间里的柱子和玩家放的柱子，长得一样、数据也一样，
但归属不同。** 前者是内容的形状（不存），后者是玩家的动作（要存）。
世界用 `world.props` 单独记着后者，存档只抄 `props`，不抄 chunk。
混在一起的话，要么玩家放的东西关窗就没，要么改一个房间尺寸就要写存档迁移。

三条顺序上的硬要求（每一条错了都只在特定条件下才暴露）：

1. 读档要在世界和玩家都就位**之后**：它要替换整个世界里的刚体、挪玩家。
2. **先清空再重建**。反过来的话读一次档数量就涨一轮，而这个 bug 只在第二次读档时出现。
3. 清空后必须让 `api` 忘掉所有 handle，否则 mod 下一次 `api.pos(h)` 会读一个已释放的对象。

还有一条属于"别让存档替内容做决定"：**`props` 里不记录"它是静态的"。**
读档时重新问一遍内容"这东西现在还静不静"，所以有人把一个原型改成
`dynamic = true` 之后，旧存档里的那根柱子读回来会变成会滚的箱子——那是正确行为。

### 生成菜单：零硬编码（✅）

`Tab` 打开。**菜单里没有一行内容是写死的**：

```
项   = pack.spawnables()       有 model 且不是 abstract
     ∪ 背包里有库存的 id        但内容已经不在了的 id 不进菜单（点了必然失败）
名字 = 内容的 name 字段        没有 name 时退回 id
标注 = ·固定（places_as_rigid == false）
     ×n（背包里有 n 件）
排序 = 背包里有的在前 → 会动的在前 → 同组按 id
```

**背包里的东西和凭空生成的东西在同一份清单里**，玩家不需要理解两者的区别 ——
对他来说都是"我要放这个"。区别只在内部：有库存就先扣库存，没库存就凭空造。
分成两栏会让玩家每次都要想"我刚才捡的那个在哪儿"。

往 `content/` 里加一个 TOML，菜单里就自动多一项——**这就是验收标准**：
如果加内容要动 `ui/spawn_menu.gd`，说明"内容即数据"在某处漏了。

菜单和 mod 走**同一个通道、同一份预算**（`api.spawn`）。分开两套的后果是
"玩家能无限放、mod 不能"，那预算就成了只约束好人的规矩。

`api.spawn` 返回 `{ok, handle, dynamic, reason}` 而不是一个 handle：静态物没有物理身份，
它本来就没有 handle，用 `0 == 失败` 会让"放下了"和"没放下"无法区分，
而一个只会说"失败"的菜单会让人以为整个功能坏着。`reason` 是给人看的一句话，
会被原样显示在状态栏。

**明确的取舍**：菜单打开时鼠标交给 UI，视角冻结。所以"瞄哪儿放哪儿"不是靠鼠标，
而是靠**手那条射线的落点**（见下一节的准星）：菜单关着的时候你已经在瞄了，
打开菜单选一项，东西就落在圈里。打不到东西时退回"正前方固定距离"。

### 准星：射线的显示，不是射线的定义（✅）

准星是一个 3D 的环，画在**手那条射线打到的地方**，不是屏幕中心。

为什么不是屏幕正中的一个十字：第三人称相机在身后 3.8 米，屏幕中心和手的射线
指向的不是同一个点。画一个屏幕中心准星，玩家对着它按右键，拿走的却是别处的东西 ——
那种错位没有任何提示，玩家只会觉得"右键有时候不准"。

两个状态，颜色区分：

| 状态 | 颜色 | 含义 |
|---|---|---|
| 瞄着自己的东西 | 亮青（微微呼吸） | 右键能收，左键能抓 |
| 瞄着房间/地板 | 灰白 | 右键什么也不会发生 |

三条实现上的硬要求，每一条都是踩出来的：

1. **不测深度**（`no_depth_test`）。第三人称往脚下瞄时，准星正好落在自己背影后面。
   一个被自己挡住的目标指示器等于没有 —— 第一次截图就是这么失败的：环一直在，只是看不见。
2. **要一圈黑边**。这个世界的配色是大块的青和橙，青环画在自己的青衣服上等于没画。
   黑边只露在外面一圈，不能垫在下面当底 —— 那样读作"一个带黑底的点"，而玩家要的是"一个圈"。
3. **打不到东西就不画**。留着上一帧的位置比不画更糟：
   那是一个"看起来指着某处、其实什么都没指"的圈。

`can_collect()` 的判断顺序必须和 `collect()` 一模一样。两份判断某天分叉的表现是
"准星亮着但按了没反应"，而玩家只会报告"右键有时候不管用"。探针同时断言
"圈可见 / 圈说可收 / hands 说可收 / 瞄着的确实是我的东西"，就是防这个。

### 收：背包，以及为什么它必须存在（✅ 见 ADR 0010）

右键把瞄着的东西**收进背包**。这个动作看着是便利，实际是**预算的必要条件**：

造物上限 96 件。在"收"之前没有任何办法把它还回去 —— 玩家放满 96 件之后
沙盒就死了，只能重启。**能放不能收，不叫沙盒。**

四条边界，每条都有对应检查：

| 边界 | 为什么 | 谁保证 |
|---|---|---|
| 收下要**归还预算** | 否则"我明明收起来了还是放不下" | 预算表按节点身份记账（`_made`），收的时候一起销账（✅ 探针） |
| **房间自带的障碍收不走** | 它们是内容的形状，搬走会在世界留下一个既不属于内容也不属于存档的洞 | `world.remove_thing` 只认 `bodies` / `props`（✅ 探针） |
| 手上拿的东西不被误收 | 射线正对着手里的箱子 | `collect()` 跳过当前持握物 |
| 装不下的**什么都不做** | 先拿走再发现装不下 = 东西凭空消失 | `collect()` 先查 `bag.can_add()` —— 满仓和满叠都算装不下（✅ 探针） |

预算记账为什么不是个计数器：收下要能**归还**，读档要能**重新认领**上次造的东西。
两件事都要求"哪几件是我造的"这个信息本身存在，而计数器不记得任何人的名字 ——
于是删掉的东西照样占着额度，读一次档额度还会清零（可以无限刷）。

**背包是世界的第一个非物理状态**：里面的东西不是节点，不参与物理、不占预算、
不合批、不剔除。它只记 id 和件数，**不记位置**——「放出来」是重新造一件，
不是把某个具体的物体搬回去。一旦要记位置，就得在背包里模拟一个静止的世界，
那是另一个项目，而且和"存档只存玩家的动作"这条分界直接打架。

`entity.remove` 钩子与 `entity.spawn` **严格对称**：只有拿过 handle 的东西才发。
静态物从来没被 `entity.spawn` 通知过，也就没有"离开"要通知 ——
对它发等于朝契约撒谎（mod 会拿一个永远为 0 的 handle 去查）。

`world.remove_thing()` 返回**被拿走那件的内容 id**，空串表示"不归我"。
返回 bool 会让玩家那条路再查一遍"刚才拿掉的是哪个"，而那时节点已经 `queue_free` 了。

### 拾取与堆叠：pickup 从死数据变成规则（✅）

`pickup` 组件的两个数都被引擎读，而且都是**内容说了算**：

| 数 | 谁强制 | 不守约会怎样 |
|---|---|---|
| `stack`（堆叠上限） | 背包 `add()` / `from_save()` 拒绝超限 | 玩家把 25 个骨符塞进 20 一叠 —— 手改存档也压回去 |
| `value`（价值） | 背包 `total_value()` 合计显示 | 菜单状态栏的"价值"是假的 |

三条实现要点：

1. **上限只来自内容**。`pack.stack_limit()` 读 `pickup.stack`，没有 pickup 的东西
   不限叠（木箱叠几箱都说得通，写死一个数等于引擎替内容做决定）。
2. **拒绝发生在拆走之前**。`collect()` 先问 `bag.can_add()` 再动世界 ——
   反过来的话，"收了才发现装不下"就等于东西凭空消失。
3. **准星和收必须给同一个答案**。满叠时准星变灰，因为 `can_collect()`
   走的是同一个 `can_add()`。分叉的表现是"圈亮着但按了没反应"。

物品要有 `model` + `collider` 才谈得上拾取：没有它们，`item` 只存在于数据里，
谁也拿不到。**"能被收进背包"是 item 的全部意义的起点**，不是附加功能。

### 系统层：让死数据活过来（✅）

`game/scripts/systems/` 是"声明"变"行为"的地方。在此之前 `move` / `ai` /
`health` / `loot` 是**死数据**：契约里声明了、内容里填了、引擎一行都没读，
菜单里的"骨行者"放下去是个雕像。

| 系统 | 读 | 写 | 干什么 |
|---|---|---|---|
| `locomotion` | `move` `ai` | 速度、朝向 | 四种 brain：idle 站着 / patrol 绕家游荡 / charger 追玩家 / ambusher 伏击 |
| `vitals` | `health` `loot` | 血量、世界里的东西 | 撞击受伤、每秒回血、死了掉落、离开世界 |

四条实现要点，每条都是从"看起来对"的错法里挑出来的：

1. **写速度，不改位置。** 东西是刚体，直接改 transform 会把物理推到一边 ——
   箱子推不动它、它也推不动箱子，"扔个箱子砸它"这条链路就断了。
2. **伤害是物理的产物，不是数值系统的产物。** 唯一的伤害来源是撞击速度
   （门槛 6 m/s），没有"攻击力"这种抽象数值。能扔得出去，就要能砸出后果。
3. **会走的东西锁旋转。** 判断依据是 `move.speed > 0`（数据），不是形状也不是名字 ——
   一个没有 `move` 的胶囊是桶，它就该滚。
4. **两个系统不许互相认识。** locomotion 不知道血量，vitals 不知道移动。
   契约的 `check_system_order` 守这条：一旦互相认识，执行顺序就成了隐式依赖，
   改一下顺序行为就变，而且没有任何提示。

**mod 系统跑在同一张表后面**（✅）：`runner.gd` 先跑这两个引擎系统，
再按 `(priority, id)` 跑 `schema.extensions.systems` 里声明的外部规则。
外部规则不碰 `world.bodies`，只经 `system_api.gd` 拿 handle 与声明过的组件字段；
状态按 handle 存在内存里，物体消失就清掉。写法与边界见 §5 ② 和 ADR 0011。

**掉落走 `api.spawn`**，和玩家手动放东西同一个通道、同一个预算。后果是世界满了
时候掉不出来（东西直接消失）。这是刻意的：两条造物通道意味着两个预算，
而两个预算一定会一个紧一个松。如果掉落物经常吃满预算，就该把预算改成
"世界里刚体总数上限"而不是"玩家造物上限"——这是这个决定的推翻条件。

**掉落表是内容**（`kind = "loot_table"`，`entries = [{id, chance}]`），
`loot.table` 指向它的 id，编译期查悬空引用。为什么不是引擎里的一张字典：
mod 要能加自己的表、也要能用 patch 覆写别人的表，两条路都要求表可寻址。

> **代价要如实记下**：怪物从"钉住的障碍"改成刚体之后，房间里那 9 个实例
> 从合批的 9 个 instance 变成了 9 次独立绘制（物理身份没法合批）。
> 现在 888 三角形 / 23 次绘制，仍然是零头；但"静态合批"这条优化的适用面
> 变小了 —— 它现在只服务房间装饰。同屏刚体数是接下来最需要盯的数字。

### 渲染：卡通着色（✅ 见 ADR 0006）

`StandardMaterial3D` 已全部换掉。两个 pass：主 pass 在 `light()` 里把 `N·L` 量化成
两级色阶加边缘光；描边 pass 用 `cull_front` + 沿法线外扩，随视图距离缩放。

三条必须记住的事实：

- Compatibility 喂进 `light()` 的 `LIGHT_COLOR` 与 Forward+ **不是同一量级**，
  只除以 `PI` 会整片过曝。所以有个显式的 `light_gain` 标定旋钮，它的值是实测的，不是物理量。
- 描边让每批提交翻倍，所以它是**可选能力**：地板和世界底板显式不挂描边 pass。
- 这套东西能做出色阶、描边、正确的头身比，**做不出原神的脸**——那需要贴图与 blend shape，
  属于资产管线，是 P3 的事。

### 物理

- 碰撞体只有三种图元（capsule / box / sphere），不做网格碰撞。
- 胶囊的"总高"要么由内容给 `height`，要么按人形比例推导（直径 × 2.8）。
- 刚体的质心显式设成几何中心。不设的话 Godot 会围着节点原点（脚底）转，
  扔出去时物体会像陀螺一样甩，而不是像箱子一样翻。
- `CharacterBody3D` 默认只是被刚体挡住、**不会推动它**。玩家控制器里主动给冲量，
  否则"物理世界"会退化成"一堵会掉的墙"。

### 两个集合：可见 vs 激活（📐 还没分开）

这两个最终必须分开，不能合成一个"在不在附近"的判断：

- **可见**：在视锥内、在视距内。要提交渲染。
- **激活**：在激活半径内。要跑逻辑和物理。

```
可见但不激活  = 远处看得到，逻辑冻结   ← 省钱的关键状态
激活但不可见  = 就在你背后，逻辑还在跑 ← 音效和威胁感需要它
```

混成一个判断是最常见的架构错误：要么远处的东西也在跑 AI（费 CPU），
要么背后的怪不会绕过来打你（玩法坏了）。

**现状**：逐实例剔除已上线（`game/scripts/world/culling.gd`）——距离 + 视锥，
每件每帧判一次"画不画"，`world.props` 里的静态物和刚体都在判定范围内
（探针五条断言，含与 Godot `is_position_in_frustum` 的逐件对拍）。
剔除**只回答"画不画"**，不动物理、不冻逻辑 —— 顺手关模拟是最容易埋雷的"优化"。
可见与激活仍然共用一个判断；分开它们要等"激活半径"这个概念真的有了需求。

## 7. 预算由系统强制，不由内容自觉

内容层可以无限扩张，帧预算必须封闭。已强制的和待建的：

| 预算 | 状态 | 强制方式 | 越界表现 |
|---|---|---|---|
| 每帧钩子事件 | ✅ | `bus.gd` 上限 256，超出丢弃并计数 | 某个事件失效，不是掉帧 |
| 造物（玩家 + mod） | ✅ | `api.MAX_SPAWNED = 96`，动态与静态共用一份；拆掉一件归还一件 | `spawn()` 返回 `ok=false` 和理由，`refused` 计数 |
| 钩子节拍 | ✅ | `tick` 固定 0.25 秒，不给每帧机会 | mod 只能"活着"，不能"每帧算一遍" |
| 激活实体 | 📐 | 超出激活半径的实体不跑逻辑 | 远处的怪站着不动（正确行为） |
| 物理体 | 📐 | 每 tick 碰撞对数上限 | 极端堆叠时新物件进入"休眠" |
| 动态光源 | 📐 | 只点亮最近的 N 盏 | 第 N+1 盏灯不亮（不是掉帧） |

造物预算刻意**不分**"玩家的"和"mod 的"：分两套的话，预算就只约束好人。
静态物也计入，因为它虽然不参与模拟，但它的碰撞体永久占用物理查询——
"不动的物体不要钱"是错觉，只是便宜。

这段思想来自一次实测：原来 30000 条内容里可见的发光体有 45 个，全部点亮直接超预算，
而内容层完全看不出来自己做错了什么。**设计上不禁止，但越界会被系统收走。**

核显档要特别记住一条：**每多一盏实时光源，片元要多算一遍，而它算的像素和你屏幕一样多。**
屏幕分辨率才是真正的乘数——宁可降内部渲染分辨率再放大，也别加灯。

## 8. 确定性与实测（📐 迁移后待重建）

开放架构有个隐藏前提：**同样的内容必须产生同样的行为**，否则"改了 A 导致 B 异常"
永远查不出来。三条（📐 尚未在 Godot 侧建立）：

1. **固定步长**模拟（30Hz），渲染帧率再高也不影响逻辑。
2. **每个实体独立种子**：`seed = world_seed * 1000003 + entity_id`。
   不用全局随机数生成器——那样加一个实体就会改变其他所有实体的随机序列。
3. **系统顺序由 priority 决定**，写入冲突直接拒绝启动。

已经做到的那一小半：房间填充用的是 `rng.seed = hash(room_id)`，
房间之间互不干扰；mod 合并按 id 字典序，不依赖目录遍历顺序。

### 归档的数字还能用，但要认清它测的是什么

`legacy/cpp-renderer` 留下过一组数据：内容从 100 条涨到 30000 条（300 倍），
帧开销只涨 3.6%；同样 30000 条内容，最好的摆法和最坏的摆法差 9.4 倍。

**这些数字测的是"静态实例渲染"，不是沙盒的真实负载。** 沙盒的瓶颈是物理和网络。
还留下两样确实有用的东西：分块/激活半径，以及"预算由系统强制"这个思想。

诚实的一条：那组数据是在 llvmpipe（软件光栅）上测的，合批只值 20%。
**软件光栅的提交几乎不要钱，真显卡不是。** 这条结论要真机验证。

## 9. 反模式

| 反模式 | 后果 | 现在由谁拦住 |
|---|---|---|
| `if archetype == "bone_walker"` 这种按 id 分支 | 每加一种内容就要改代码，架构名存实亡 | `lint_arch.py` R4（✅ 会失败） |
| 把引擎行为挂在内容里的魔法字符串上（`tags` 里的 `"abstract"`） | 写错一个字母，规则就静默失效 | `TOP_FIELDS` + `abstract` 字段 + 编译器自测（✅） |
| 注释里写着规则，代码里没做 | 规则不存在，而且看起来像存在过 | 编译器自测 + 探针（✅ 抓到过一次） |
| 用 `0 == 失败` 表达造物结果 | 静态物没有 handle，"放下了"和"没放下"没法区分 | `spawn()` 返回 `{ok, handle, dynamic, reason}`（✅） |
| 能放不能收 | 玩家放满预算后沙盒就死了，只能重启 | 右键收进背包 + 预算归还（✅ 探针） |
| 用计数器记预算 | 删掉的东西照样占额度；读一次档额度清零，可以无限刷 | 按节点身份记账 + 读档认领（✅） |
| 收 = 删 | 删掉不可逆，玩家不敢动自己刚摆好的东西 —— 从另一个方向把沙盒锁死 | 收进背包，可以再放出来（✅ 探针） |
| 背包里记位置 | 等于在背包里模拟一个静止的世界，和"存档只存玩家的动作"直接打架 | 只记 id 和件数（✅ ADR 0010） |
| 准星画在屏幕中心 | 第三人称有视差，玩家对着准星按，拿走的却是别处的东西 | 画在射线落点上（✅ 探针） |
| 堆叠上限写死在引擎里 | "20 一叠"是内容的决定，写进代码后改平衡要发版 | `pack.stack_limit()` 读 `pickup.stack`（✅ 探针） |
| 满叠先拆走再拒绝 | 东西凭空消失，玩家以为游戏在偷他的东西 | `collect()` 先 `can_add()` 再动世界（✅ 探针） |
| 在 `scripts/mods/` 之外运行时编译 GDScript | 多了一个没人审查的代码注入入口 | `lint_arch.py` R7（✅ 会失败） |
| 相信 mod 自己声明的级别 | 带脚本的 mod 只要写成 `data` 就绕过授权 | 编译器与引擎各算一遍（✅） |
| 基础内容里写 `kind="script"` / `kind="system"` | 有一条通道绕过授权闸门，而且最容易被忽略 | 编译器自测 + 自检（✅ 都会失败） |
| 系统之间直接互相调用 | 执行顺序变成隐式依赖，改一处崩一片 | L4 读写集 / 优先级由编译器与运行时检查（✅）；内置系统仍靠 review（📐） |
| 内容文件里写脚本 / 表达式 | 校验失效，mod 变成任意代码执行 | 编译期只认已注册的 id（✅） |
| 给引擎底层开扩展点 | 帧率无法保证，没人能定位是谁搞坏的 | 靠 ADR 约束（📐） |
| 全量遍历所有实体 | 内容越多越卡 | （📐 待用空间网格） |
| 存档里存静态世界 | 改一个房间尺寸就要写迁移代码，而它保护的是"上次的样子" | 靠 ADR 0008（📐 review） |
| 目录叫 `utils` / `common` / `helpers` | 三个月内吸收一切垃圾 | `lint_arch.py` R1（✅ 会失败） |
| 单文件写到 2000 行 | 下一个 agent 读不完就瞎改 | `lint_arch.py` R2（✅ 会失败） |
| 剔除顺手把物理和逻辑也停了 | "看不见"变成"不存在"：远处的怪不掉血、东西不落地，bug 藏在视距里 | `culling.gd` 只回答"画不画"（✅ 探针） |
| 视锥判据的正负号靠猜 | 写反了**不报错**，只是"画 2 剔 17"或全画，看起来像性能问题 | 与 Godot `is_position_in_frustum` 逐件对拍（✅） |
| 探针断言写死绝对数量（`== 14`） | 内容加一件东西验收就红，下一个人会把断言改松，而不是查原因 | 断言用"存档那一刻"的相对基准（✅） |
| 改了内容/契约却用旧的 mod 编译产物 | 旧 pack 按 id 覆盖，把新字段盖回旧值 —— 改动静默丢失，最难查 | `check.sh` 第 2 步每个 mod 都从源重编（✅） |
| 契约里注册了组件，引擎里没人读 | 菜单里的"骨行者"放下去是雕像，名字像怪，实际是摆设 | 契约 vs 实现清单对照（✅ 现在 13 内置读 9，缺口写在 §4） |
| mod 直接拿节点 / Transform3D / 组件对象 | 第一天就把引擎内部结构钉死，之后再也不敢重构 | `system_api.gd` 只给 handle 与字段动词（✅ 第 10 步探针） |
| mod 自定义组件覆盖内置组件，或两个系统撞优先级 | 语义被悄悄改写、执行顺序靠字典遍历 | 编译器 + `validator.gd` 各拦一次（✅ 自测） |
| 把 L4 可变状态塞进存档 | 卸载 mod 后存档里留下一堆没人认识的数据，也没法迁移 | `extension_state.gd` 只在内存里，按 handle 清理（✅ 第 10 步探针） |
| 把 `:=` 用在 untyped 的 `app.pack` / `world` 返回值上 | Parse Error 只在加载脚本那一刻炸，编译期完全没提示 | 显式写类型 + `no_engine_errors()`（✅ 第 5/10 步都抓到过） |
| 运行时把 JSON 里的 48.0 当成"不是整数"直接拒绝 | 编译产物合法，却把无辜的 data mod 整包挡在门外 | `validator.gd` 接受整数值的小数、拒绝 1.5（✅ 自测 + 自检） |
| 固定节拍掉帧时追补一串规则 | 卡顿被放大成"规则突然跑十遍"，雪崩 | `runner.gd` 一帧最多补一次（✅ 探针） |

**架构纪律写在文档里，agent 会忘；写在 `check.sh` 里，agent 绕不过。**

## 10. 为什么是 Godot（见 ADR 0001）

不是性能，是**四样平台必需的能力它都内置**：资源覆盖、运行时脚本、物理、导出单包。

自研 C++ 渲染器曾经跑通过（能走、能截图、3 万条内容 3 次 draw call），
但试玩后放弃：它只解决了渲染，还缺碰撞、资产管线、音频、UI、导航、输入映射——
**任何一项都是一年**。代码在 `legacy/`，只读归档。

留下的是三样资产：内容层、契约层、以及那组数字基线。
**内容和契约是资产，渲染器是可替换的执行层。**
